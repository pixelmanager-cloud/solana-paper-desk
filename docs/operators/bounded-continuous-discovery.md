# Opt-in bounded continuous discovery

This tool records original migration-authority-filtered notifications only. It never creates scans, investigations, history requests, paper entries or monitoring requests. Provider entitlement/pricing and connection/duplicate/control/oversize billing remain unknown. Payload limits are application message bytes, not wire/TCP/HTTP/WebSocket framing, pings or provider credit guarantees. No service is enabled by this change.

Use the separate reviewed tool checkout as working directory; existing paper services must remain on their pinned release. No files under `desk/` change, so its implementation fingerprint remains unchanged. Stop the old discovery timer/listener before any supervised opt-in run: two different database paths would create two budgets. This tool owns one fixed coordinator-managed DB; do not delete, replace, restore older copies, change IDs, or create another DB to refresh allowance. Preserve original launch archives. Existing backup tooling does not automatically include this new database; coordinator must arrange an offline consistent backup without counter rollback.

Explicit initialization (new dedicated DB; existing DBs refused):

```sh
python -m discovery.continuous init --db /var/lib/solana-desk/discovery/continuous.sqlite --address 39azUYFWPz3VHgKCf3VChUwbpURdCHRxjWVowf5jUJjg
python -m discovery.continuous status --db /var/lib/solana-desk/discovery/continuous.sqlite
python -m discovery.continuous listen --db /var/lib/solana-desk/discovery/continuous.sqlite --seconds 86400
```

The listener reads only managed `CREDENTIALS_DIRECTORY/provider-keys.json` (bounded16KiB, owner/group-read modes), never prints keys/URLs/provider exceptions, and opens no inbound listener. The inactive service template has no Install section, timer or restart policy. Initialization is an explicit coordinator operation; listen never initializes missing/invalid databases. Single-writer flock rejects concurrent callers and path aliases.

User-selected initial policy:100000000 authorized payload bytes/hour OR5000 observation slots/hour,2400000000/day OR120000/day,5368709120bytes(5GiB) storage. Message bound200000bytes and12 connection attempts/hour remain fixed. Policy is durable and immutable on normal resume; explicit `configure --db PATH --hour-bytes N --hour-records N --storage-bytes N` appends a policy revision while preserving every reservation, frame and used counter. No implicit upgrade from older limits occurs. Smaller policies remain available for fixtures/operator restrictions; values above the selected maximum are rejected. Before each receive, the full200000-byte maximum and one potential observation are durably reserved. A known completed message charges its actual UTF-8 bytes and whether an original observation was stored; duplicate/control/malformed frames still consume bytes and are retained. Failures and exclusive-restart recovery conservatively consume the full reservation and an observation slot; no interrupted read is refunded. If fewer than200000 bytes remain, listening pauses even though smaller messages might fit. Original accounting/frames are append-only, clock rollback refuses, resets are absent.

The selected5GiB storage ceiling includes database and journal/WAL/SHM files. The DELETE-journal DB stops4MiB below the selected ceiling to leave transaction/journal headroom, and SQLite page growth is bounded. Smaller64MiB fixture policy stops at60MiB. No pruning or rotation resets budgets. Unexpected WAL/storage modes, disk/commit failures, conflicts and oversize messages stop without accepting prefixes or claiming complete evidence. Original response content that could not be captured remains an explicit gap.

Quiet receive timeouts preserve the same connection and pending reservation; ping settings remain20seconds. Real transport failures use exponential2–60second backoff and persist connection attempts. At budget exhaustion the socket closes and the process checks eligibility at most once/minute without fresh subscriptions or counter resets. Every interruption/reconnect/cap pause leaves coverage unverified; connected status is not finality or coverage proof. `last_payload_at` differs from `last_stored_at`; raw events never grant candidate or entry authority.

Investigation18, daily10, queue3 and open-position monitoring60/hour are unchanged. The observed withdrawal authority is a dynamic discovery hint, not a fixed authenticated program constant; rotation/unrelated account uses and both token programs can appear. Admission/finalized migration evidence still require separate existing bounded workflows.

New observations remain available to existing tooling: `raw_events` retains `seq,source_id,received_at,slot,payload` (plus an additive payload hash); full original UTF-8 notification JSON is in payload and exact received bytes in frames. Run the existing `python -m desk decode-capture --db NEW_DISCOVERY_DB --output NEW_DECODED_JSONL` from the pinned/tool release to inspect them. Extract observed migration mint/pool/signature/slot from original parsed instructions using the existing decoder, then pass those public hints to the existing manual `python -m desk.migration_slot_intake` workflow with its original admitted scan/evidence paths. A raw confirmed slot is a hint, never finalized migration evidence. The decoder output uses exclusive creation; do not overwrite archived originals. Existing launches.sqlite stays unchanged and can be inspected separately.

The reviewed schema2 stores a monotonic reservation watermark atomically before I/O and validates contiguous original reservation identity/count on resume. Partial restores retaining metadata but missing failed-only attempts, frames, raw observations or their charged receipts refuse without reconstruction. Schema1 development prototypes are not production-compatible and are preserved/refused; this tool performs no schema migration, budget adoption or repair. Policy changes on a valid schema2 DB preserve all usage and originals.
