# Bounded paper-entry history page size

Base: integration `9504728`. Fresh paper-entry pool windows request 50 full parsed finalized transactions per page instead of 100. The response cap remains 2 MiB, request deadline unchanged, lifetime investigation ceiling 18, feature page ceiling eight, and feature aggregate ceiling 2 MiB/256 records. No provider calls were made.

Only the paper-entry window selects 50. Other history producers retain their existing default 100, including original-byte slot discovery grammar. Optional strictly integer `page_size` is bound into new query identity and coverage digest, propagated through continuation/seed, checked against returned row count and reproduced against exact retained request manifests. Existing queries and coverage without this field still mean 100; their identity, bytes, hashes and replay remain unchanged. No SQLite schema migration or historical row update is required. Old software will fail closed when replaying new 50-row evidence because its expected request differs. Changed desk source requires a separately reviewed runtime transition before deployment.

This reduces per-page response risk, not total evidence requirements. A single unusually large transaction still fails RESPONSE_OVERSIZED. More pages may exhaust the unchanged eight-page or shared 18-request limits. Partial histories remain non-exhausted, withhold measured-window coverage and cannot fabricate volume or completeness. The existing failed preparation/NULL pass and its 7/18 charges are not edited or retried; retirement remains a separate coordinator dependency.

Synthetic tests use unchanged public mainnet transaction structure with explicitly synthetic signatures/time/log padding and mocked HTTPS only. Fifty full parsed records fit under the unchanged transport cap while 100 equivalent records exceed it; two pages replay 100 unique observations across restart with exact cursor and two charges. Additional tests cover legacy 100-row replay, seed continuation, changed page-size binding, invalid types, server over-return, giant transaction charge/failure retention, eight-page truncation and prior16 + two reads exhausting18 without measured-window promotion. Tests establish transport/replay behavior, not real candidate acceptance or authenticity.

Validation results will be recorded in the PR at its exact head; full Linux suite and independent09 review are required before coordinator integration.
