No production implementation, schema/migration, acquisition publication, receipt/entry wiring or prior scan retrofit is introduced. Unaccepted PR94 is excluded.

## Exact existing capability

`ownership_acquisition.acquire` already requests `getSlot([{"commitment":"finalized"}])` after confirmed legacy mint validation. On a successfully saved cutoff C, it calls HistoryProgress.create with `{gte:0,lt:C+1}`. `history.collect_history` replaces blockTime filtering with that exact slot filter in getTransactionsForAddress. Successful pages retain history_request_v1(method, params, response_hash), and immutable acquisition setup binds the saved getSlot logical response. Existing documentation cites the Helius slot gte/lt API; no unsupported parameter is needed or proposed:

- https://www.helius.dev/docs/api-reference/rpc/http/gettransactionsforaddress
- Existing repository references: docs/readiness.md301 and docs/deployment.md326. These prior citations are repository evidence, not fresh cloud provider validation.

The new probe checks the actual committed reservation using another SQLite connection inside the synthetic callback. At getSlot, used=2/ceiling18, mint_hash is saved, cutoff_hash is NULL, exactly one mint page is persisted, and no stage/request intent exists. After a successful slot20 response, the original persisted logical record is exactly method=getSlot, params=finalized, result=20; the real history callback and persisted manifest both contain filters.slot={gte:0,lt:21}. Source calls=3 and the same budget includes all attempts. Once saved, a terminal restart makes zero I/O and retains byte-identical evidence/source.

This positive capability does **not** establish the requested pending-before-I/O or exact original-wire contract.

## Reproducible gaps

1. **Charge lacks durable stage/request intent.** In ownership_acquisition.py195-200, generic HistoryProgress.reserve commits the used increment, then rpc returns, then _Setup.save persists the logical observation. HistoryProgress.reserve170 commits no method/params/fence/session/PENDING event. A process dying before setup publication leaves a spent count and NULL cutoff, without evidence identifying the spent stage or whether its observation is already ambiguous. Counter values cannot safely identify stage: earlier mint failures can consume the same counts. HistoryProgress.advance has a generic PENDING history checkpoint but permits charged retries and saves its request manifest after I/O; it is not the new terminal original-request capability.

2. **Real returned-slot loss changes the later discovery bound.** A spawned fixture process runs actual public acquire/SQLite/queue/admission/mint validation, receives getSlot20, and exits121 immediately before _Setup.save(cutoff). An fsynced external *synthetic fixture trace* proves reservation1=mint, reservation2=slot20; it is not production evidence or a substitute cutoff record. Production state is ADMITTED, used2/18, saved mint, no cutoff page/hash. Reopening the SAME scan currently invokes getSlot900, then history with {gte:0,lt:901}; one shared budget reaches4, no reset/refund occurs, and eligible_for_trading remains false. Original mint evidence survives; unsaved slot20 cannot be reconstructed from production records. This is a confirmed violation of the newly requested terminal-ambiguity/no-cutoff-drift contract, not a claim that previously saved cutoffs move. Existing successful-cutoff recovery tests cover a later boundary and do not cover this window.

3. **Result-only transport cannot preserve original wire identity.** providers.helius_rpc returns result["result"] (providers.py48). The synthetic mock proves distinct response IDs1/99 collapse to scalar20; this legacy adapter does not validate their IDs. The hardened coordinator_rpc.HeliusMainnetRPC validates framing but still returns only _result(parsed_raw) at147. Distinct original whitespace/field-order bytes collapse to the same20. Neither API exposes actual request bytes, bounded original response bytes or failure provenance to acquisition. Passing a full original JSON-RPC slot envelope to acquire instead of scalar result is strictly rejected, charged, unpersisted and does not start discovery. Wrapping20 into fabricated framing would not restore original bytes.

4. **Accepted fixed coordinator transport cannot acquire discovery.** coordinator_rpc._METHODS21 allows only getGenesisHash/getSlot/getMultipleAccounts/getBlockTime/getTransaction. It excludes getTransactionsForAddress (also getAccountInfo). The executable probe calls its actual public adapter with the existing supported logical slot-filtered history options and verifies rejection BEFORE any credential lookup or opener/network construction. Extending a local whitelist would need independent protocol/provisioning review and desktop provider validation; it is not evidence the accepted transport supports this method.

5. **Post-SEALED journal cannot bootstrap its own input.** CommonBankJournal._source requires exact SEALED admission/source, and plan reconstruction requires original discovery. Actual create_run on the fresh interrupted ADMITTED acquisition refuses before run creation; original tables/admission/counter remain unchanged. Its accepted atomic genesis/slot intents are post-discovery, cannot supply an earlier original cutoff, and cannot be reused to rewrite prior sources or derive a fictitious cutoff from later T.

## Smallest decision and missing inputs

There is no implementation meeting all requested guarantees through the accepted acquisition/transport contracts. No provider parameter was invented and no permissive adapter or schema side channel was added.

The minimal next decision is to independently authorize a **fresh pre-SEALED acquisition-stage protocol and byte-preserving single-request transport extension**, separately from migration/publication/receipt/entry work:

- Bind fresh admitted job/DB identity, original shared18 admission descriptor, trusted fixed source/network/genesis configuration and exact stage before I/O. Atomically reserve the same counter and append immutable original getSlot(finalized) PENDING intent in one transaction. Do not infer intent from used counts or convert/retrofit old setup records.
- Expose generated original request bytes/ID and bounded unchanged response bytes or fixed redacted failure through one same-live-session completion capability. A restarted/lost-ack PENDING is terminal, with no I/O retry/refund/new-ID escape. Known identical result persistence may be acknowledged only under the audited live capability. Strict actual integer cutoff and overflow-safe C+1 derive only from the retained original slot result.
- Bind each initial/paginated history request to that exact completed cutoff and cursor; atomically reserve shared18 plus immutable request intent before I/O. Preserve the whole original response/request chain, failed/ambiguous attempts and original data. Do not take bounds from later common-bank T, normalized completeness flags or caller-supplied cutoff.
- Review the fixed transport's exact existing getTransactionsForAddress grammar and byte caps/source provisioning; desktop alone validates provider support using already authorized access. Cloud has made no provider calls and has no authenticated production slot/history observations to supply.

This is a concrete protocol decision, not a general readiness inventory or request for routine execution approval. Existing slot filter grammar is supported by code and prior citations; required durable attempt/session identity and raw transport outputs are missing. The successor must not assume unaccepted PR94, migrate/publish old sources, relax Token-2022, permit entries or claim source/finality/ownership authentication.
