## What changed
1. **Checkpoint validation** (`Ledger._portfolio_state`, called from `_checkpoint` on every `apply`/`report`).
   Reads the ledger's saved config. Flag off: neither key may exist. Flag on: `portfolio_entries` (when present) is a
   non-empty list of at most `K` non-negative ints, strictly increasing, none after `last_ts`, last element
   consistent with `last_entry_minute`; `portfolio_cooldown_until` (when present) is a positive int not beyond
   `last_ts + M minutes`. A **missing** key is an error whenever the checkpoint proves it must exist: entries once
   `last_entry_minute >= 0`, cooldown once `loss_streak >= N`. All violations are the standard
   `ledger checkpoint invalid: recovery required; original records preserved` `ValueError` (never a reset, never a bare
   `TypeError`; a test also asserts the tampered state is left untouched).
2. **Reject records.** `PORTFOLIO_RISK_CAP` now carries `reasons`, `scores`, `bundle_audit` and `entry_policy` (when a
   policy is selected) next to `size_sol`/`open_risk`/`limit`. `BELOW_MINIMUM` carries the same audit fields **only with the
   flag on**; with the flag off it is byte-identical (tested), because it exists in every historical journal and the
   checkpoint reader replays journals. This is why I did not simply add the fields everywhere.
3. **Liquidation and the loss streak: decision = liquidation closes count.** The portfolio cooldown follows the
   engine's `loss_streak`, which has always counted every full close including `LIQUIDATE` (and halves size at 4,
   pauses at 6). A forced exit at a loss extends the streak and can start the cooldown; at a profit it resets the
   streak. Rationale: consistency with the engine and fail-closed (it can only delay entries). Documented in
   `docs/PORTFOLIO_RISK.md` and pinned by three tests (loss -> cooldown ends exactly at `exit_ts + M`, profit -> reset,
   two liquidated losers renew from the same exit time). No behaviour changed here, so these tests are GREEN on base; the
   mutation "liquidation closes do not count" turns them red.
4. **Config validation.** `portfolio_max_entries_per_10m` must be `1..10` (`PORTFOLIO_MAX_ENTRIES`); `ENTRY_THROTTLE`
   allows one entry per minute, so a larger limit could never bind.

## Remaining limitations
- A deleted key is only detectable when the checkpoint proves it must exist. Before the first entry, or after a win cleared
  the streak while a cooldown was still running, an absent key is indistinguishable from a deleted one, because the engine
  writes the keys lazily (T31's design and tests). Making the guarantee total would need `initial_state` to seed
  `portfolio_entries: []` and `portfolio_cooldown_until: 0` when the flag is on (a state-shape change; then every
  checkpoint must contain both). I did not do it: it changes flagged state shape and T31's own assertions, and was outside
  the stated scope.
- A flagged ledger written by T31 code without these checks and with a tampered/inconsistent state would now require
  recovery. No flagged ledger is deployed (T31 is not integrated).
- The validator does not replay the journal to recompute `portfolio_entries`/`portfolio_cooldown_until`; it checks types,
  ranges and consistency with `last_ts`, `last_entry_minute`, `loss_streak`.
- `desk/paper_checkpoint.py` (separate cycle-time checkpoint reader, not in scope) does not know these keys; it is unchanged.
