## Design decision (read this first)
The decision says "append-only `pacing_policy_changes` row ... never an in-place silent edit". I went one step further: **the original `policy` rows are never edited at all.** Reason (verified in code): `desk/kraken_pacing_migration.read()` re-checks on every validation that the non-Kraken `policy` rows still equal the migration receipt's `old_policy` ("Original pacing policy changed"). Editing `helius`/`jupiter` there would make every `Pacer(...)` fail on the production DB, which carries the Kraken receipt. So the reviewed change lives only in the new table, and the *effective* cadence/backoff of a provider is its newest change row (`_effective`). Side effect: `tools/verify_kraken_successor_originals.py` (which compares the original policy rows) is unaffected.

## What changed
- `desk/provider_pacing.py` (policy path only, +~170 lines)
  - `pacing_policy_changes` table (exact schema + guards pinned like `pacing_reclaims`: no UPDATE/DELETE, rows must arrive with the next id, `provider IN ('helius','jupiter')` so Kraken can never get a row). Columns: provider, old/new cadence, old/new backoff, reason, `config_sha256` (sha256 of the policy file bytes), `policy_digest` (digest of the reviewed entry), applied_at.
  - `_validate` accepts the table and validates the whole chain on every `Pacer` construction: ids 1..n; each row starts from the provider's previous effective value (the original policy row for the first); `policy_digest` must be an entry of THIS release's `config/provider-pacing-policy.json`; new values and reason must equal that entry; real/text types, finite numbers, non-decreasing times, 64-hex sha, row cap 64. Kraken is still pinned exactly (`(2, 2.0, 30.0)`). A missing/corrupt policy file while the table exists fails closed (`PACING_DATABASE_INVALID`).
  - Effective values are used where cadence/backoff were read from `policy`: `acquire` (next_at), `throttle` (30 s fallback backoff), `_reclaim` and `reclaim_orphans` (grant-age arithmetic).
  - `policy_plan(path, id)` (read-only) and `apply_policy(path, id)`: refuses unless no grant is pending and no live waiter (expired waiter rows are ignored), refuses on clock rollback, creates the table/guards on first use, records one row per provider whose effective value differs (idempotent: `ALREADY_APPLIED` / `NOTHING_TO_DO`), validates the chain inside the transaction BEFORE the commit (failure rolls back) and the whole database again afterwards.
- `config/provider-pacing-policy.json`: one reviewed entry, `2026-10-11.paid-developer-plans.1`: helius 0.1 s (10 req/s = 20% of 50), jupiter 0.25 s (4 req/s = 40% of 10), backoff 30 s. The file is an append-only list (a later entry chains from the previous one; removing an entry orphans its rows and fails closed).
- `tools/ops/pacing_policy.py`: `plan` / `apply` (dry run unless `--execute`). `apply --execute` first re-checks that every unit that opens the shared pacing DB is inactive/failed (entry dispatcher service+timer, held cycle service+timer+path, counterfactual, fill-realism worker, dashboard, plus `--require-quiesced`; same `tools.ops.backup` check, unknown state = not quiet) and that `--policy` is this release's reviewed file.
- `docs/ops/RUNBOOK.md`: new step 6b (while every writer is still stopped), the mixed-version note, the per-provider budget note (Helius `getMultipleAccounts` = one RPC call; DAS/Enhanced have their own 10 req/s cap; Jupiter's 60 s sliding window and firewall 429 below the quota), and how to change it later. `tests/test_ops_e2e_deploy.py` still passes (the new section is outside the steps it executes).

## Tests (`tests/test_pacing_policy_upgrade.py`, 43 tests)
Production-shaped fixture: `provider_pacing.initialize` at 2.0 s + the real reviewed Kraken migration (receipt, kraken policy and state rows) + non-zero state; fake clock; fake units.
- Kraken policy row, state row, receipt rows and schema are byte-identical after apply; the original helius/jupiter `policy` rows are identical; Kraken still paces at 2.0 s; `config/kraken-pacing-migration.json` unchanged.
- New cadences take effect (measured grant gaps: before 2.0 s, after about 0.1 s / 0.25 s, never faster than reviewed); a 429 with no Retry-After still embargoes for 30 s, a `Retry-After: 120` is honoured, a later entry's backoff (60 s) is used; reclaim arithmetic uses the effective cadence.
- Re-apply is a no-op (bytes identical); partial state records only the difference; nothing-to-do does not add the table; refuses on a pending grant, a live waiter, a clock behind the high-water; chaining a second reviewed entry; removing the first entry from the file invalidates.
- Forged rows rejected: unknown digest, altered values, chain break, altered reason, bad sha, time going backwards, `inf`, Kraken row (CHECK), out-of-order id (guard), id gap with the guard dropped and recreated, text in a numeric column, UPDATE/DELETE blocked, dropped guard, edited stored value, edited reviewed file, missing/corrupt reviewed file, first row claiming a wrong old value, a wrong-schema table, row cap.
- Old code: the extra table makes the previous validation rule fail (emulated with the constant an old release lacks): documented as fail-closed; before apply old and new code both accept the database.
- CLI: dry runs write nothing; `--execute` needs every writer quiet (each of four units tested, unknown state, extra units); refuses relative/dotdot/symlink/missing db, another policy file, unknown id; non-quiescent db blocks.

**Fail-first:** on `integration/r1` the module cannot import (`tools.ops.pacing_policy` / `apply_policy` do not exist): `FAILED (errors=1)`. **Mutation checks:** 35 single-point mutants of the new code (effective-value lookup order, digest/chain/value/reason/id/schema/type/time/sha/row-cap validation, quiesce checks, expired-waiter handling, idempotency, pre-commit validation, backoff/cadence/reclaim use, OSError fail-closed, policy-file shape and bounds, clock check, CLI policy pin, canonical db, dry-run default, unit check and list, UNKNOWN state, readiness flag, extra units): 33 killed, 2 survive as **equivalent** mutants (the Kraken exclusion in `_effective`, which the CHECK constraint makes redundant, and the `typeof` column checks, whose effect `_number` also provides). The first run had six survivors that exposed real test gaps (id continuity, row cap, `_db` canonicality, UNKNOWN unit state); they now have tests.

## Remaining limitations
- `desk/provider_pacing.py` changed, so the runtime implementation hash changes (rotate to a new ledger when flat; a pacing DB shared across ledgers stays shared).
- The default quiesce list names `desk-fill-realism-worker.*`, which may not exist yet (an unknown unit reports `inactive`, which passes). `desk-held-watcher` is deliberately not listed (it uses its own allowance, not the shared pacing DB).
- The tool cannot know about an ad-hoc process (a shell, a cron job) that opens the DB; the database-level check (no pending grant, no live waiter) is the only guard there, and a process started with older code fails closed afterwards.
- No automatic rollback: to return to 2.0 s, append a new reviewed entry in a new release (the chain stays append-only).
- Nothing measures the real Helius/Jupiter limits; the 20% / 40% headroom is the decision's, not an observation.
