# T06 — Paper round-trip + cold-restart verifier

Branch `cloud/T06`, BASE `r1-base` (`c1e22c2`). Owns: `tools/ops/verify_cycle.py`, `tests/test_ops_verify_cycle.py`. No file under `desk/` was touched, so the runtime implementation hash is unchanged.

## What changed
`python -m tools.ops.verify_cycle snapshot --data DIR --ledger NAME --config PATH --out snap.json [--research --evidence --pacing --journal]`
`python -m tools.ops.verify_cycle compare A.json B.json [--allow-progress]`

Snapshot (read-only, no locks taken, no provider I/O):
- Validates the ledger like the support script does, but generalised: saved config hash/canonical config equal the supplied config, journal complete, `validate_checkpoint`, every fill labelled `EXECUTION_UNVERIFIED`, every fill bound to a journaled event at/before the checkpoint with the same mint/provenance, no duplicate fill identity.
- **Per-position attribution** (mint + entry fill seq/event/hash). A second BUY into an open mint, a SELL with no open entry (sell-before-buy or oversell), a sell not strictly after its entry, a pool/taker identity change, exact raw inventory imbalance (when `quote_execution.mint_decimals` is present) and cost-basis imbalance are all errors. Open positions and closed round trips are reported separately. Open positions report token, time, size, entry price, label.
- Cash/PnL: `cash == initial + sum(fill cash flows)`, `realized_pnl == sum(sell pnl)`, per-position `qty/cost_left/trade_pnl` equal the fills, and the identity `cash = initial + realized − cost still held` (tolerance 1e-18). Status: `NO_FILLS | OPEN_POSITION | VALIDATED_LIVE_DATA_PAPER_ROUND_TRIP` (plus `provenance` / `all_live_capture_provenance` so a synthetic ledger cannot be mistaken for live capture).
- Records checkpoint digest, `last_ts`, config/implementation hashes, fills with identities, event/outcome counts and max seq, monitoring budget (cap, total used, pending reservations, high-water, duplicate-reservation groups), ownership budgets, pacing state/high-water, dispatcher journal counts, plus cumulative row digests ("rolling") for append-only tables.
- Output file is created `O_EXCL|O_NOFOLLOW`, mode 600; never overwrites. Store names must be plain names inside a canonical `--data`; symlinked files refused.

Compare: strict mode requires identical comparable content (fills, checkpoint, budgets...). `--allow-progress` requires old fills to be a prefix, old rolling digests of events/outcomes/monitoring/journal rows to reappear unchanged, counters and high-waters monotonic, ownership `ceiling`/`source_hash` unchanged. Duplicate fills, config/implementation change, or a newly appearing duplicate monitoring charge fail in both modes. Exit 0 PASS, 1 FAIL, 2 error (corrupt/missing evidence is never a pass).

Read-only detail found by test: a plain `mode=ro` read of a quiesced WAL database creates `-shm`/`-wal` files (root-owned if run as root). Quiesced databases (no -shm, empty/no -wal) are now opened `immutable=1`; with live sidecars, `mode=ro` is used without creating files.

## Limitations
- Fixtures use the real engine (constant-product fills) with the label added to stored payloads; real quote-mode fills (raw-inventory path, `quote_execution`) are exercised only through the code path, not with a full live-shaped fixture. The engine currently holds one position at a time (T16), so multi-position fixtures are sequential (closed + open), not concurrent.
- Table/column names for monitoring, ownership, pacing and dispatcher journal were taken from `desk/` DDL; file names default to `research.sqlite`, `evidence.sqlite`, `provider-pacing.sqlite`, `entry-dispatch/` (overridable). Absent stores are reported as `present:false`, not invented.
- "Duplicate monitoring charge" = same (scan, mint, checkpoint, method, params hash) reserved twice; this is a heuristic and may need tuning against production data.
- Does not call `require_runtime` (so it works from any release dir); it reports the stored implementation hash and fails compare if it changes.
- Snapshots taken while a writer is active are not guaranteed to be mutually consistent across stores (each store is one read transaction).
- Restart is not itself "verified" by one snapshot; `restart_verified` is only implied by a PASS compare across a real restart. Forward observation/profitability are not claimed.

## For the coordinator
- No deploy or migration; nothing under `desk/` changed. Usable from the release dir against live stores read-only (as an unprivileged user preferably) or store copies.
- Suggested use: `snapshot` before stopping services, restart, `snapshot` again, `compare` (strict); use `--allow-progress` for later checks.
- Conservative defaults chosen: any unlabeled fill fails; a never-initialised ledger errors instead of reporting NO_FILLS; tolerance 1e-18 (support script used 1e-20).
- Commit trailer: used the session's attribution lines; the worker prompt's "Opus" trailer was not copied because it would misstate the author.
