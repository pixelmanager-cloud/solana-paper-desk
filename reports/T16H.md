# T16H — Concurrency: post-intent checkpoints must not orphan the intent; TTL-independent rollover

Branch `cloud/T16H`, BASE `origin/cloud/T35` (contains T16G) + merge of `origin/integration/r1`. `desk/` changed: the implementation hash changes; rotate store sets.

## What (per item)
1. **Orphaned intents (HIGH).** `tools/paper_entry_dispatcher.py`: `_HeldCadence.checkpoint` now returns a halt record when the held pass exits non-zero, moves the mode off `RUNNING`, leaves an exit unresolved, reaches max positions, or leaves monitoring blocked. The dispatcher then writes a typed terminal result `dispatcher_checkpoint_no_entry_v1` to the journal (`checkpoint_record`: phase, sorted reasons, held-pass `ran`/`exit_code`, mode, `no_retry`), verified in `_check_records` (`_checkpoint_record_valid`: exact field set, dispatch id, scan id, intent hash, phase/reason enums). The charges stay charged; the next preflight validates the journal normally; held monitoring proceeds. The failure code is surfaced in the dispatch result (`checkpoint_no_entry.held_pass.exit_code`) instead of being swallowed.
2. **Rollover.** `engine.rollover_after_mark` no longer requires `paper_portfolio_mark_ttl_seconds`. With T35's batched marks the marks event itself rolls the day over when every position's valuation mark is fresh (<= 10 s, the price TTL). Tested with 3 positions and no TTL key: book full / no candidate, `EXIT_ONLY`, ledger with room; a missing position, a blocked exit or a stale observation defers it.
3. **Flag dependency.** `paper_concurrent_entries_version` no longer requires the TTL key (`pc.selected`). The old assertion that raised on "flag without the key" was loosened on purpose, with the reason in the test and the commit message.
4. **Docs and reports.** `docs/MULTI_POSITION.md`: every recommendation of the key removed (marked REJECTED, kept for the record), activation steps rewritten, `ENTRY_SECONDS` figure corrected to 52; correction notes at the top of `reports/T16F.md` and `reports/T16G.md`. The engine docstring says the key is a non-recommended knob that nothing depends on.
5. **Phase caps.** `PHASE_CAPS` = acquisition 30 s, intake 25 s (2.5x the planning figures). `_Phase.check()` runs before each acquisition request and in the intake before-I/O callback, so no request of an over-cap phase starts; `_Phase.finish()` catches a phase that ended late. Either way the intent ends as the typed result with reason `PHASE_CAP_EXCEEDED`. The checkpoint rule now uses the caps as the next-phase seconds. Preparation and the cycle keep their existing code caps (18 s, 10 s deadline).

## Limitations (honest)
- A phase cut mid-way leaves the acquisition/intake partly done. The scan is terminal for the dispatcher journal, but this was only exercised on the synthetic stores; the global terminal gate accepted the stores in every tested case.
- An acquisition request that is charged by `progress.reserve` and then cut by the cap stays charged without a provider call (append-only, conservative).
- The caps are planning-figure multiples, not measurements. A late-finishing phase is also refused (conservative: the entry is dropped even though its data arrived).
- `monitoring_blocked`/non-zero held codes always end the entry, including benign transient leg failures; the next entry attempt proceeds normally.
- The key `paper_portfolio_mark_ttl_seconds` and its engine validation still exist (T16F tests use them); only the dependencies and recommendations were removed.
- The rollover tests are engine level (3 synthetic positions). The marks event path through the real pipeline is covered by T35's tests.

## For the coordinator
- Conservative defaults chosen: any non-zero held code is terminal for the entry; caps 30 s / 25 s.
- The typed result is a new journal result kind; a reviewer should confirm `_check_records` should also pin it in any historical-journal continuation tooling.
