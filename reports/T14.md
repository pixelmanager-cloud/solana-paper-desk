## What changed and why
Explicit, versioned, opt-in config key `paper_fill_realism_version: 1` (absent = off, requires `paper_quote_execution_version: 1`; validated in `qe.config`). When on, every simulated BUY and SELL fill produced by `paper_cycle.run_once` is followed by re-quotes of the same route/input at +2s, +5s, +10s after the decision event.

- `desk/fill_realism.py` (new): sample scheduling, drift math, append-only persistence, reporting math.
- `desk/quote_execution.py`: 3 lines in `config()` so a malformed flag fails config validation everywhere.
- `desk/paper_cycle.py` (T01 overlap, minimal): import; `realism_jobs=[]`; after each `deliver(event,quotes)` a guarded `fill_realism.collect(...)`; in the existing `finally`, after `ledger.close()`, a guarded `fill_realism.measure(...)` that never raises. Nothing else touched.
- `tools/research/fill_realism_report.py` (new): read-only report, `python -m tools.research.fill_realism_report --ledger L`.

Design decisions
- Measurement runs after the item loop (in `finally`), not inside it, so it never eats the 10s cycle deadline of the real decision and never delays another item. It does hold the cycle/worker/evidence locks for about 10s per fill-producing run.
- Each attempt goes through the existing charge-verifying classes (`_Budget` for investigation admissions, `_HeldBudget` for the monitoring allowance), via a fresh deadline per sample whose attempted-counters are synced back (so the 18-per-cycle cap still holds). A failed or invalid response is charged and recorded (`status=FAILED`, code, `charged=1`). Refused/skipped samples (late, reserve, exhausted) record `charged=0` and make no request.
- Storage: table `paper_fill_realism_samples` created lazily inside the LEDGER file (only when the flag is on). PK `(fill_event_id, side, delay_seconds)`; BEFORE INSERT trigger binds each row to an existing ledger event with the same `ts`; BEFORE UPDATE/DELETE triggers abort; `execution_status` CHECK = `EXECUTION_UNVERIFIED`. Stores raw ints, the original re-quote JSON and its hash, and derived drift strings. The recorded fill, events, outcomes, state/checkpoint are never written.
- Drift (signed bps): `out_drift_bps = (requote simulated out / decision simulated out - 1)*1e4`; `adverse_slippage_bps = -out_drift_bps` (positive = worse than the paper fill); `price_drift_bps` on SOL-per-token from estimated outputs.
- Latency-adjusted PnL: every leg re-priced at the delayed re-quote; proceeds also scale with the delayed BUY token ratio; fixed fees unchanged. Legs with a failed/missing sample are never imputed (trade counted as unmeasured for that delay).
- Report re-verifies every sample (decision fields equal the fill's recorded quote record, requote hash, recomputed drift) and excludes + lists anything that fails (`integrity_errors`).

Findings that shaped the design (found by tests, not assumed)
1. The 18-read admission is shared by entry and legacy (non-monitoring) held passes (9 entry + 4 mark + 4 exit = 17). Three entry samples made the later exit fail with `SHARED_REQUEST_BUDGET_EXHAUSTED`. Fix: an investigation reserve of 8 reads is kept whenever the position is still open and the monitoring allowance is not provisioned (then only 1 entry sample fits); with monitoring provisioned there is no reserve.
2. The monitoring allowance can fund quotes only for an OPEN position (`MONITORING_OPEN_POSITION_REQUIRED`). So after a full exit, sell re-quotes are charged to the scan's investigation admission through a plain source; after a partial exit (position still open) they are charged to the monitoring allowance, keeping 16 reads of headroom.

## Remaining limitations (honest)
- A re-quote is not a fill. It measures quote drift of the same route/input N seconds later; it does not include transaction landing time, priority-fee/Jito effects, failed or dropped transactions, MEV, or partial fills. Real latency is probably worse than this measures.
- One sample per delay per fill; no confidence interval (needs many trades; T10 owns forward stats). The delay is a wall-clock sleep, accurate to roughly the quote round trip; actual elapsed seconds are stored.
- Mint age for the re-quote uses a relaxed freshness (`ttl + delay + 18s`) because the typed mint comes from decision time; the re-quote itself must be fresh under the TTL.
- With monitoring NOT provisioned, entries get only 1 of 3 samples (by design, to protect exits). Under provisioned monitoring a full exit's 3 sell samples consume 3 investigation reads (about 15 of 18 per scan in total).
- A process kill between the charge and the row insert loses that sample (the charge stays charged, never refunded or retried).
- The report does not re-verify the ledger checkpoint (it is read-only and independent of `read_checkpoint`).
