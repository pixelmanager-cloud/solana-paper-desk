## Findings and fixes
1. **Outcome classification** - the old code read only `result.blockers/reason`, so on REAL dispatcher writers (reproduced with the BASE module on the dispatcher fixtures) a BUY and a COST_BUDGET engine rejection were both `ADMITTED:COMPLETE`, and a token rejection was `ADMITTED:NO_RESULT`: the "does the filter reject winners?" report was invalid. New `classify_result` parses every stored shape (`dispatcher_token_rejection_v1`, `dispatcher_migration_no_entry_v1`, `history_preparation_no_entry_v1`, `paper_cycle_v1`), and `OutcomeReader` joins the journal, the ledger and the decision store read-only (opened ONCE per pass). Classes: `BOUGHT`, `REJECTED:<stage>:<code>`, `NOT_DISPATCHED`, `UNKNOWN`. Priority: ledger BUY fill > typed journal result > decision-store rejection (`paper_candidate_decision`, `decision=REJECT`) > NOT_DISPATCHED. A store that cannot be read, an unresolved dispatch, a recovery-required cycle, a corrupt row or an unknown result kind is `UNKNOWN` with a detail code, never guessed, never a normal rejection, and a missing/unreadable decision store never turns a candidate into NOT_DISPATCHED.
2. **Survivorship** - `POOL_DEAD` is -100% at that horizon and at every later horizon without a priced sample of its own (a later priced sample is trusted); it stays in the return statistics (`dead_at_horizon`) and in `pool_died`. A pool dead at +5m counts as -100% at every horizon (`dead_at_baseline`).
3. **Fixed baseline** - the +5m sample for every candidate. A missing/missed/failed/unpriced baseline excludes the candidate from the return statistics (`baseline_missing` counted per group) and never re-baselines to a later horizon.
4. **Service template** - the store lives in its own subdirectory (`<root>/counterfactual/counterfactual.sqlite`); `ReadWritePaths` = that subdirectory plus `/var/lib/solana-desk` (needed because the shared pacing database is a rollback-journal file and SQLite creates `provider-pacing.sqlite-journal` beside it; a file-only entry is not enough); the experiment root and the discovery directory are `ReadOnlyPaths` (deeper path wins in systemd's mount namespace, so only the counterfactual subdirectory is writable inside the root). All read-only opens follow the T02F rule (`open_mode`: `immutable=1` only for a quiet WAL file, header byte 18 == 2 and no `-wal`; rollback-journal stores such as discovery are `mode=ro`, which works with no `-shm`). New `desk-counterfactual.timer` (60 s after the previous run finishes: no overlap, a failed run is retried on the next tick) is the restart policy. `systemd-analyze verify` accepts both units (only complaint: the venv path does not exist in this container).
5. **Backfill** - a new store starts at the first discovery frame young enough to still have a horizon left (`received_at >= now - (6 h + grace)`); frames older than that are skipped WITHOUT decoding, also after a long outage when a cursor already exists. The cursor is persisted before decoding anything.
6. **Minor** - a `null` pool account is retried with backoff (60 s doubling, capped at 15 min; each try is a charged request recorded in the new append-only `vault_attempts` table) until the 6 h window has passed, then recorded `UNRESOLVED` once (`POOL_ACCOUNT_NULL_WINDOW_PASSED`, or `WINDOW_PASSED_BEFORE_RESOLUTION`); a present-but-invalid pool account is still `UNRESOLVED` once at once. `refresh_outcomes` opens one journal/ledger/decision view and re-reads only candidates whose latest outcome is not final (typed results and BUYs are final; NOT_DISPATCHED becomes final after the 7200 s dispatch window plus grace). `set-allowance` accepts 1..3600 (grace 0..3600) and the CLI exits 2 otherwise. Stores created before `vault_attempts` get it (append-only triggers) on the next `sample`.

## Limitations (honest)
- The service sandbox was checked only with `systemd-analyze verify` (syntax), not run under systemd; the "deeper path wins" layering of `ReadWritePaths`/`ReadOnlyPaths` should be confirmed on the VPS (`systemd-run -p ReadWritePaths=... -p ReadOnlyPaths=... touch`), and `/var/lib/solana-desk` stays writable for the old archived stores except through file permissions.
- A candidate with several rejection reasons appears in several groups; sums over groups are not candidate counts.
- Classification is as good as the stored result kinds; an unrecognised new kind is `UNKNOWN`, never a rejection.
- Prices are research-only quote-vault spot prices, not fill evidence; the +5m baseline is an observation 5 minutes after the migration, not the migration price.
- Discovery frames are decoded in batches of 500 per run; a very long backlog of YOUNG frames is caught up over several runs.
- A decision-store rejection only classifies candidates without a journal intent; the decision store has no timestamps, so it is not used for timing.
