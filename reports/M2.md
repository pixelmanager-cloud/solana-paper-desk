## The three bugs (audit B01/B02, REPORT "Why the L19 learner finds nothing")

| | Old (`learn.py:139-146, 582-591, 674-677`) | New |
|---|---|---|
| (a) test | t-test of the **rejected** PnL against **0**. Every window loses (−0.04 to −0.08 SOL per candidate), so any rule that rejects enough "gains". | **Kept vs rejected** difference in mean PnL per candidate under the same exit policy: Welch one-sided t **plus** a random-rule null (≥ 1000 seeded random rules that reject the **same number** of candidates in the same time blocks). A rule must beat the null's 95th percentile (and have a permutation p ≤ α). |
| (b) windows | One 50/25/25 split. The 6 h embargo dropped 41/101 select and 73/101 confirm rows. `min_n` 50 > 0.8 × 60, so nothing could be selected. `min_confirm` counted rejected rows. The same confirm window was re-tested every 3 h. | A newest **confirm holdout** (30 %, at least 2 × `min_confirm`). Older rows whose label window crosses into it are **purged** (only on the dev side; confirm rows are never dropped). A **purged rolling-origin CV** runs on development, with embargo = `path_hours` between each training set and its test block. Support **adapts** (10 % of the training set, clamped to [10, `min_n`]). `min_confirm` now applies to **both** groups. A confirm block is tested **once**: a ledger in the selection files means a later run can only confirm on fresh candidates (`CONFIRM_PENDING` + ETA until then). |
| (c) objective | `−sum(rejected)/n` rewards "stop trading". A 93 %-reject rule was confirmed while the kept 7 % still lost. | The mining objective is **gain over a random rule of the same size** (`n_rej·mean − sum(rej)`). Reject share is **capped at 70 %**: in mining, out of fold and on the chosen union; coverage is reported. A proposal needs **kept mean PnL > 0 after costs**. A set that beats the null but still loses is `BLEED_REDUCER`: reported, **never** proposed. |

## How the learner decides now

1. **Windows** (`plan_windows`, index ranges only, no PnL read):
   * Confirm = the newest `max(⌈0.3·n⌉, 2·min_confirm)` enterable candidates.
   * Dev = older candidates whose decision is at least `embargo_s` before the confirm block's first decision.
   * Dev is cut into `folds` = 5 blocks. Block k (1..4) is a test block. Its training set is the dev candidates before it whose
     decision is at least `embargo_s` earlier. Block 0 only ever trains.
2. **Mining per fold:** the greedy 1/2-condition miner (unchanged shape), ranked by gain over random. The support is
   `support(n_train)` and the reject share is ≤ 70 %. Thresholds are quantiles of the dev window's **feature values** (label-free), so a
   rule recurs across folds.
3. **Out-of-fold test:**
   * Each distinct mined rule is scored on the test blocks of the folds that mined it (pooled), via Welch on kept vs rejected.
   * **Benjamini-Hochberg over every tested rule** (count reported in `tested.rules`).
   * Survivors must beat their random-rule null, stratified by block.
   * Flags: `INSUFFICIENT`, `REJECTS_TOO_MUCH`, `NO_GAIN`, `NOT_SIGNIFICANT`, `NOT_ABOVE_NULL`.
   * Each rule gets a `kind` of `PROFITABLE` or `BLEED_REDUCER`.
4. **Set:** up to 3 eligible rules, greedy by out-of-fold gain over random. Each must add rejections and gain on dev, and the union
   must stay ≤ 70 %.
5. **Confirm, once:**
   * The set is tested on the confirm block: both groups ≥ `min_confirm`, Welch p ≤ 0.05, above the null's 95th percentile with
     null p ≤ 0.05 (1000 draws).
   * Kept mean > 0 gives `CONFIRMED`. Otherwise it is `BLEED_REDUCER`. Failing the test gives `NOT_CONFIRMED`.
   * The block is recorded as consumed (`evidence.confirm_consumed`, `split.confirm_end_ts`) in the selection file.
6. **Ledger** (`consumed_confirm_until`, read from the run's own `proposals/` dir):
   * A v3 file counts as consumed if it says so.
   * A v2 file whose outcome was `CONFIRMED`/`NOT_CONFIRMED` counts as consumed up to its run time (from its name).
   * An **unreadable file fails closed**: it counts as consumed up to the time in its name.
7. **ETA** (`confirm_eta`): hours after the newest candidate until a run has a feasible **and** fresh confirm block, at the observed
   enterable rate. It is found by doubling then bisecting over synthetic arrivals through the same planner. It is in
   `feasibility.eta_hours` / `needed_enterable`, on the HTML page, and in the CLI summary line.

The CLI's `--embargo-s` now defaults to `paths.path_hours × 3600` from `--config` (the recorder default is 6 h without it). The deployed
unit's explicit `--embargo-s 21600` still works. `--fractions` is gone. The new flags are `--confirm-fraction --folds
--max-reject-fraction --alpha --fdr-q --null-draws --seed`.

### Design notes and things I rejected

* **Blocked K-fold (train on both sides) was tried and rejected.**
  * It pooled each rule over the folds that mined it, so one test block's outcomes decided whether another block was pooled.
  * Under the global null it "discovered" rules on dev in **15-20 %** of pure-noise worlds (12/60 and 9/60).
  * Rolling-origin makes inclusion depend on the past only. It measured **2-3 %** (3/100 noise, 2/100 losing noise), within BH's 5 %.
* **BH uses the Welch p-values; the permutation null is a second gate.** With 1000 draws the permutation p floor is 0.001. With m ≈ 60-100
  rules, BH on that floor would need several rules tied at it.
* **The 70 % cap is not re-applied to the confirm block's realised share.** On a 12-row block the share is noisy. The
  `test_e2e_risk_external` world's correct rule rejects 9/12 = 75 % there and ~50 % on dev. The set was capped on dev, and the confirm
  still needs ≥ `min_confirm` kept candidates. The "stop trading" test shows the cap is what stops a 90 %-reject rule: lifting it to 95 %
  confirms that rule.

## Limitations

* **Selection bias remains.** The chosen set is the best of many; BH and the single-use confirm bound it, they do not remove it. A
  proposal still needs a forward paper run under a new strategy version.
* **The pooled out-of-fold test is approximately valid, not exact.** Inclusion is predictable, so it behaves like a martingale sum, and
  it measured within BH's 5 % on synthetic nulls. The confirm block is the exact gate.
* **The ledger lives in the run's own `proposals/` dir.** Deleting those files resets it. Runs with `proposals_dir=None` (analysis)
  keep no ledger.
* **The labels still use the vault mark** (`labels.mark_lamports` → `adapters.mark`). When M1's flagged mark lands, `labels.py` should
  pass the same flag so the learner labels with the live mark. That is a follow-up after M1 merges; I did not touch `adapters.py`.
* **Hazard rejects have no paths (audit B04),** so the learner can still only tighten. Exits are where the money goes (B05), and that
  is out of scope.
