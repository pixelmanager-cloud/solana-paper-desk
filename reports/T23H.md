## Reproduction and root cause
`python -m unittest tests.test_empty_history_successor_lifecycle` failed with
`PacingError: PACING_CLOCK_INVALID` raised from `Pacer.reclaim_orphans()` (called by `terminal._pacing`, the gate of
`paper_dispatch_preparation_retirement.review_plan`). The same error made all 28 tests of `test_paper_preparation_retirement` error on `cloud/T23F`
(found while testing T31F). Tracing `Pacer._now` showed the cause:

- The lifecycle fixture advances the pacing database with an injected fake clock that runs ahead (it steps 0.05 s per read starting at the real time),
  so `MAX(high_water)` ended ~10 s in the future.
- The gate builds its own `Pacer(path)` with the real `time.time`: `now (…115.3) < high_water (…125.3)` => `_now` raises.
- `reclaim_orphans` caught only `sqlite3.Error`, so the `PacingError` escaped from the gate. Clock and validity rule are the same as
  `acquire` (`self.clock`, `_now`), so the contradiction is genuinely in the inputs; the bug is that a read-first helper raised.

## Fix
`Pacer._reclaim_now(c)` wraps `_now`: a `PACING_CLOCK_INVALID` returns `None`, any other `PacingError` is still raised. `reclaim_orphans`
uses it on the read-first pass AND after `BEGIN IMMEDIATE` (rolling back), returning `[]` in both. Nothing is reclaimed on an untrusted
clock; `acquire` keeps its fail-closed `PACING_CLOCK_INVALID` check, and a gate still refuses on a pending grant ("Provider outcome
pending"), so no new unresolved path appears. The fixture clock was left alone (the fix is at the root, not the test).

## Remaining limitations
- The lifecycle fixture still uses a clock that runs ahead of the gate's real clock; it now passes because the gate no longer crashes on that
  disagreement, not because the clocks agree. In production there is one wall clock.
- With a clock behind `high_water`, `_pacing` passes a database that has nothing pending: provider calls are then refused by `acquire`
  (`PACING_CLOCK_INVALID`), exactly as before; the gate was never meant to judge the clock.
