# T08 — Held-exit robustness

Branch `cloud/T08`, BASE `r1-base` (`c1e22c2`). All evidence is synthetic (`SYNTHETIC_TEST_ONLY`);
no provider, VPS or production store was touched.

## Verdict (read this first)

Two independent wedges stop a held position from ever exiting after a *single* failed held pass.

| ID | Wedge | Where | Status |
|----|-------|-------|--------|
| **W1** | One transient read failure (`TRANSPORT_ERROR`, deadline, HTTP 408/429/5xx) latches `paper_monitoring_budget.blocked='SOURCE_FAILURE'`. Nothing clears it, so every later held read raises `MONITORING_RECOVERY_REQUIRED`. | `desk/monitoring_budget.py` `retain_outcome` | **Fixed here** (prospective). |
| **W2** | Any held pass that is not `COMPLETE` and charged ≥1 request leaves `paper_observation_passes.outcome_hash` NULL. The global gate then returns `OBSERVATION_RECOVERY_REQUIRED` for every later pass, **held passes included**, and for every future entry. | `desk/paper_cycle.py:678` (only COMPLETE or zero-charge passes get an outcome), gate at `desk/paper_terminal_reconciliation.py:544/:583`, called from `desk/paper_cycle.py` before the held loop | **Not fixed**: both files are T01's. 4 RED `expectedFailure` tests + proposal below. |

Answer to question 5: **yes.** A failed exit attempt leaves a NULL pass that survives the later successful
exit and blocks every future entry (`test_failed_exit_attempt_leaves_null_pass_after_the_exit`,
`test_W2_next_entry_candidate_is_not_blocked_after_exit_that_needed_a_retry`). In production this is the same
class of one-off reconciliation that T01 is removing for *entry* rejections; T01's scope (verified no-entry
rejections) will not cover held passes unless it is extended.

## What changed
- `desk/monitoring_budget.py`: new `_latching_failure(record)`. A failed attempt is still reserved, charged, and its
  outcome retained (`paper_monitoring_reservations` / `paper_monitoring_outcomes` unchanged), but the one-way
  `SOURCE_FAILURE` latch is skipped for `TRANSPORT_ERROR`, `DEADLINE_EXCEEDED`, and `HTTP_REJECTED` with status
  408, 429 or 5xx. Everything else still latches: 401/403 and other rejections, `RESPONSE_INVALID`,
  `RESPONSE_OVERSIZED/TRUNCATED`, `OUTCOME_PERSISTENCE_FAILED`, `KRAKEN_*`, unknown codes. Nothing is reset or
  rewritten; already-latched stores are read exactly as before (the readers still accept `SOURCE_FAILURE`).
- `tests/test_monitoring_budget.py`: `test_failure_charged_original_retained_and_restart_latched` used a transient
  `OSError` as its sample failure and so pinned the old behaviour. **Loosened deliberately** (reason is in the test
  comment): it now uses a non-transient failure (HTTP 200 with a wrong JSON-RPC envelope → `RESPONSE_INVALID`); the
  latch assertions are unchanged. New `test_transient_failure_charged_original_retained_and_not_latched` covers the
  transient case, including that the secret sentinel is not retained and the next read is charged.
- `tests/test_held_exit_robustness.py` (new, 14 tests).

## Case results

Harness: the real `PaperReadSources` transport, collector, `fulfill_quotes`, engine, ledger, `MonitoringBudget` and
terminal gate against the Kraken-USD fixture (`tests/test_kraken_lifecycle.actual_cycle`); only wire bytes and the clock
are injected. A STOP exit is forced with a held sell quote of 500 000 lamports (expected proceeds 0.000442525 SOL after
the 0.00005 SOL fee, realized PnL −0.009607475 SOL, asserted exactly).

1. **Transient exit-quote error, then good quote.** Pass 1 → `BLOCKED TRANSPORT_ERROR` (4 requests charged, outcomes
   retained). Before: budget latched (W1) and pass 2 `RECOVERY_REQUIRED` (W2). After the fix: budget `AVAILABLE`; pass 2 still
   `RECOVERY_REQUIRED` (W2). With the gate relaxed (simulation, see below) the exit completes once, one SELL, charges =
   exactly the attempted requests, cash/PnL exact.
2. **Stale quote, then fresh.** `BLOCKED SOURCE_RESPONSE_STALE` (4 charged, no latch even before the fix). Same W2 wedge on pass 2; with
   the gate relaxed the exit completes, no duplicate fill.
3. **STOP trigger, quote source down for 4 passes.** Every attempt is charged exactly once (`reservations == outcomes == attempted
   HTTP requests`), no phantom exit, window use ≤ cap (60), then the good quote exits. When the allowance is exhausted
   the pass makes **zero** requests (`MONITORING_REQUEST_BUDGET_EXHAUSTED`) and the position stays open. (Gate relaxed to isolate budget behaviour.)
4. **Restart mid-blocked exit.** The producer cannot persist `exit_blocked`/`EXIT_ONLY` from a worthless quote: a sell quote below the fixed
   fee yields `UNRESOLVED_QUOTE_DEMAND` before anything is delivered (mode stays RUNNING, nothing persisted, 5 requests charged). Stores reopened cold: state,
   fills and budget are identical, no duplicate charge. A persisted `EXIT_ONLY` checkpoint is only produced by stale marks/unavailable routes and its restart
   behaviour is already covered by `tests/test_cloud_ledger_restart.py::test_unsellable_partial_exit_and_recovery_remain_latched_after_restart`. Recovery on the next pass is W2-blocked.
5. See the verdict.

Recovers on its own after my fix? Cases 1–4: **no** (W2). The 6 `..._once_gate_is_relaxed` / budget tests prove W2 is the **only** remaining wedge
in these scenarios.

## Remaining limitations
- W2 is unfixed. Until it is, one failed held pass with charges wedges exit **and** entry on that store set.
- No persisted `exit_blocked` scenario is reachable through the live producer in fixtures, so the engine-level `EXIT_ONLY` + restart path is only covered by the older ledger-level test.
- `KRAKEN_PROVIDER_ERROR` (Kraken `error` array, throttled via the pacer) still latches. It is arguably availability-type like a 5xx; I kept it fail-closed because
  the change is not demonstrable with the available fixtures. Candidate follow-up.
- `mode` stays `EXIT_ONLY` after a blocked exit until an operator `RESUME` control; I did not change that.
- Real-provider behaviour (Jupiter/Helius/Kraken status codes) is unverified.

- Decision made: 408/429/5xx counted as transient; 401/403 and all malformed-response codes still latch (conservative).
