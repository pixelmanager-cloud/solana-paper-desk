# T29 - Funnel report (where candidates die)

Branch `cloud/T29`, BASE `integration/r1` (97fb80d). New files only: `tools/research/funnel_report.py`, `tests/test_funnel_report.py`, this report. Nothing under `desk/` (no runtime-hash impact), no network, no provider access, no writes to any store.

## What it does
`python -m tools.research.funnel_report --discovery-db D --journal J --research-db R --ledger L [--evidence-db E] [--decisions-db X] [--counterfactual-store C] [--since EPOCH] [--until EPOCH] [--horizon 3600] [--out-html report.html]`

Prints one JSON report; `--out-html` additionally writes a single self-contained HTML file (inline CSS, no JS, no external assets, created exclusively with mode 0600; refuses to overwrite and refuses symlinks).

Cohorts = migration hints decoded from the discovery frames (same `desk.decode` + `_migration_event_hint` selection as the dispatcher and T26), bucketed by the UTC hour/day the frame was received. Per cohort (all / by hour / by day) and stage: how many candidates reached it, why the others died before it, how many are pending, request usage by ending stage, and median seconds between stages.

| Stage | Reached when |
|---|---|
| discovered | decoded unique migration hint (altered/undecodable/ambiguous frames are counted, never used) |
| selectable | not already scanned without an intent, and the 300 s age window opened |
| dispatched | journal `intents` row for the mint |
| admitted | research `scans` row for the mint |
| history_ok | typed result is not a token / migration / history-preparation rejection |
| observations_ok | cycle result `COMPLETE` (no blockers) |
| engine_eligible | no engine `reject` outcome |
| buy | BUY fill in the cycle result and/or the ledger |

Death codes come from the stored typed results: `TOKEN:*` (token policy), `MIGRATION:*`, `HISTORY:*`, `OBSERVATIONS:*` (cycle blockers), `ENGINE:*` (first engine reason; further reasons in `extra_reasons`), plus `ALREADY_SCANNED_NO_INTENT`, `EXPIRED_NOT_DISPATCHED`. `pending` = not a death yet (`WINDOW_NOT_OPEN`, `AWAITING_DISPATCH`). `UNRESOLVED:*` (dispatched but not admitted, no result row, unreadable row, recovery required, unknown result kind) is kept separate from normal rejections because it is a latch, not a rejection. Every candidate ends exactly once (BUY + deaths + pending = candidates; tested). Consistency flags: `LEDGER_BUY_NOT_IN_RESULT` (the ledger fill promotes the candidate), `RESULT_BUY_NOT_IN_LEDGER`, `LEDGER_BUY_WITHOUT_INTENT`.

Also reported: discovery frame integrity stats and truncation, unreadable journal intents, ledger fill counts, evidence budget snapshot (ownership budgets used/ceiling/exhausted, observation passes with unresolved NULL count), decision-label counts, and (when `--counterfactual-store` is given) the forward return per ending group at `--horizon` (median, share positive, pool-died; baseline = first priced `OK` sample, the same definition as T26's `metrics`).

Read-only rules (T02F): every store is canonical (no symlink, single regular file), opened `mode=ro` with `PRAGMA query_only=1`; `immutable=1` ONLY for a WAL-mode file (header byte 18 == 2) with no `-wal`, never for a rollback-journal store such as the pacing or discovery stores. Missing tables fail closed (`*_TABLES_MISSING`), they are never reported as zero counts.

## Limitations (honest)
- Cohort time is the discovery receive time. The dispatcher run times are not recorded, so "selectable" means "the 300 s window opened and the mint was not already scanned"; it cannot prove the dispatcher actually looked at the candidate while it was in the window. `EXPIRED_NOT_DISPATCHED` therefore mixes "never selected" with "selected but another candidate won".
- Result shapes are read from the stored typed results (`paper_cycle_v1`, `dispatcher_token_rejection_v1`, `dispatcher_migration_no_entry_v1`, `history_preparation_no_entry_v1`). A new result kind appears as `UNRESOLVED:UNKNOWN_RESULT_KIND`; update `classify_result` then.
- Request budget per stage uses the counts embedded in each stored result (`attempted_requests`, `budget`, or `requests_after`); results without them contribute no data (the table says `candidates_with_data`). The evidence budget snapshot is global, not per candidate.
- Frame decoding is bounded (50,000 frames, `frames.truncated` flags it); research scans and ledger fills are bounded too. Frames with an altered stored hash are only counted.
- `--counterfactual-store` expects a store with `samples(mint,horizon,status,price)` like T26's; it is tested against a fixture of that shape, not against T26's tool output (T26 is not on this base).
- Decision labels are a plain count of `decisions.decision` (`action`/`decision`/`verdict` key or the raw text); the stage funnel does not use that store.
- No statistical claims: counts and medians only.

## For the coordinator
- Nothing in `desk/` changed: no implementation-hash or successor-pin implications; safe to run against live stores (read-only, never creates sidecars next to a quiet WAL store).
- Example on the VPS (after a fresh-start, as the service user or root with `PYTHONDONTWRITEBYTECODE=1`): `python -m tools.research.funnel_report --discovery-db /var/lib/solana-desk/discovery/continuous.sqlite --journal .../entry-dispatch/dispatch.sqlite --research-db .../research.sqlite --ledger .../paper-<id>.sqlite --evidence-db .../evidence.sqlite --out-html /tmp/funnel.html`.
- `UNRESOLVED:*` rows in the report are the integrity-relevant ones (latched dispatches); treat them like the NULL-pass blockers, not like ordinary rejections.
- Judgement calls (conservative): ledger BUY wins over a missing result; corrupt rows are unresolved, never typed rejections; missing tables refuse instead of printing zeros; HTML is write-once.
