# C3 — Launchpad census (new universe #3, counts only)

Branch `cloud/C3`, BASE `origin/integration/r1`. Paper only, recording only: read-only RPC on the shared Helius LOW lane, no signing, no sending, nothing in the trader reads these rows.

## What was built
- `lean/census.py`
  - Every `interval_s` (default 600) one row per launchpad in its OWN `census.sqlite` (state dir; `census` rows and `cursors` rows, append-only by trigger, `label='CENSUS'`): `ts, launchpad, program, signatures, failed, sampled, creates_in_sample, new_count, exact, truncated, sample_mints, note`.
  - Launchpads (config-driven list, `name` / `program` / `create_log_patterns`): Raydium LaunchLab `LanMV9s…` and Meteora DBC `dbcij3L…` by default; pump.fun graduations are counted exactly from the discovery database (read-only, own cursor).
  - `getSignaturesForAddress` with an `until` cursor (the newest signature of the previous poll), then up to `max_tx_per_poll` `getTransaction` calls spread evenly over the new successful signatures. A create is a configured log pattern logged while the launchpad program is the innermost running program (`match_creates`: invoke/success stack), so the token program's own `Instruction: Initialize…` lines, an aggregator's lines and failed transactions never count; a CPI create by an aggregator counts for the inner launchpad.
  - Honest counts: `signatures` is exact (a lower bound when `truncated`), `new_count` is exact only when every successful transaction was fetched (`exact=1`); otherwise it is the extrapolation `round(creates_in_sample * ok / sampled)` with the raw `sampled` / `creates_in_sample` kept, or NULL when nothing was sampled.
  - First poll of a launchpad only sets its cursor (`BASELINE`); history is never counted as new. A shed, an error or a stop writes nothing for that launchpad and leaves its cursor alone, so the next poll counts the same transactions (delayed, not lost). No fake zero rows.
  - `sample_mints`: up to 3 non-SOL mints from `postTokenBalances` of sampled create transactions.
- Budget: Helius standard calls are 1 credit. Worst case per month is `launchpads x (max_pages + max_tx_per_poll) x 30 x 86400 / interval_s`; `config()` REFUSES a config above `credit_budget_month` (default 50 000; the default config is 2 x (1+4) x 4320 = 43 200). A runtime sliding-hour cap of `credit_budget_month / 720` calls (69 by default) enforces it as well, and `health()` shows `calls_last_hour`, `hourly_call_cap` and `worst_case_credits_per_month`. The pump.fun count costs no provider call.
- Runner hook (additive): `self.census = None`, `'census'` in `_aux_specs`' run_loop tuple, a `'census'` health entry. `__main__`: config key `census` (strict, validated at load; absent = off) and a `build_runner` block. `lean.example.json` lists `"census": {"enabled": false}` (the existing example-config tests require every key to be listed).

## Limitations
- The two default create patterns (`Instruction: Initialize`, `Instruction: InitializeVirtualPoolWithSplToken` / `...WithToken2022`) are from memory of the public IDLs and were NOT checked against a live transaction (no provider access). If a pattern is wrong, `creates_in_sample` stays 0 while `signatures` is still right, so the miss is visible. Verify with `lean.census.match_creates(getTransaction_result, program, patterns)` on a known create before trusting `new_count`.
- `signatures` counts every transaction that touches the program (swaps, claims, migrations), not creates; a busy launchpad fills `sig_limit x max_pages` (default 100) and is then flagged `truncated`. New launches above that rate are only a lower bound.
- The create count is a sample when there is more than `max_tx_per_poll` (default 4) successful transactions per interval; the estimate assumes the sample is representative (even spread over the interval, no stratification by type).
- `getTransaction` at `confirmed` can return null for a very new signature; that signature is not a sample and not retried.
- The pump.fun count reads the discovery frames through `lean.candidates.scan_new` (decoding a frame per migration) and so counts migrations, not every frame; unmatched frames are skipped like in screening. Its cursor is `seq` and, like the baseline of every launchpad, starts at the newest frame.
- The census thread shares the low lane with the other collectors; under a 429 shed it simply skips polls.

## For the coordinator
- Out-of-OWNS edits (all additive, delimited `# --- C3 ---`): `lean/runner.py` (attribute, aux tuple, health), `lean/__main__.py` (config key, load validation, build), `config/lean/lean.example.json` (`census` disabled).
- To turn it on: `"census": {"enabled": true}` in `lean.json`. Defaults: 600 s, 100 signatures, 1 page, 4 sampled transactions, 50 000 credits/month cap, patterns as above, pump.fun graduations on.
- Programs can be added without code: append `{name, program, create_log_patterns}` to `census.launchpads` (the worst-case credit check then applies).
