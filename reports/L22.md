# L22: honeypot sell-simulation entry filter

Branch `cloud/L22`, base `origin/integration/r1`. Paper only. Nothing is signed, sent or keyed. The only new RPC is
`simulateTransaction`, called on an UNSIGNED transaction with `sigVerify: false` and `replaceRecentBlockhash: true`.

## What it does
`lean/honeypot_sim.py` runs in the candidate path, after the pre-quote BUY gate and before any entry quote. It runs on the MAIN
lane because it gates entries.

1. **Scope.** The scope check makes no request; it reads the mint account bytes the screen already kept.
   - A pump-graduated legacy SPL mint (82-byte layout, mint and freeze authority revoked) gets
     `honeypot_sim=SKIPPED_STANDARD_SPL` and no call.
   - These are simulated: Token-2022 mints, any mint with extensions or a live authority, any candidate from a non-pump source
     (a source that is not `pump_graduation` or a `PumpGraduationSource`), and a mint whose bytes cannot be read.
2. **Holder.** The holder list comes from the screen's own `getTokenLargestAccounts` rows. The filter makes that call itself only
   if the screen did not keep them.
   - Excluded before any request: the pool base vault and the burn ATAs.
   - The top 6 remaining token accounts are resolved to their owners with one `getMultipleAccounts`.
   - Owners skipped: the coin creator (from the pool account), the pool, burn owners, and off-curve owners (a PDA cannot pay a fee).
   - Order is largest first. A frozen holder account is kept on purpose: its failing sell is the evidence.
3. **Build.** `Jupiter.quote(mint → SOL, amount, taker = holder owner)` uses the same `/swap/v2/build` endpoint L02/L16 use.
   - The amount is a tenth of our paper size, capped by the holder's balance.
   - The build's instructions are compiled into a v0 message with solders: compute budget, setup, swap, cleanup and other. The
     tip instruction is left out.
   - The lookup tables are the ones Jupiter returned. The payer is the holder.
   - Signature slots: exactly one, all zero. Any signer other than the holder → `NO_BUILD`. The transaction is at most 1232 bytes.
4. **Simulate.** `simulateTransaction` is called with `{encoding: base64, sigVerify: false, replaceRecentBlockhash: true,
   commitment: confirmed}`. Each result is mapped by `classify`.
5. **Full size.** If the small sell is OK and that holder holds at least our full paper size, the full size is simulated too
   (`full_size`). A BLOCKED full-size sell makes the candidate BLOCKED.
6. **Filter.**
   - `SELL_SIM_BLOCKED` → entry `SKIP` with reason `HONEYPOT_SIM_BLOCKED`. This is a hazard: it is not in the watchlist's soft
     set, so it is never re-screened.
   - `INCONCLUSIVE` or `NO_BUILD` on a risky mint → `SKIP` with reason `HONEYPOT_SIM_UNVERIFIED_RISKY`. A risky mint is a
     Token-2022 mint with a transfer hook or a transfer fee above 10 % (the larger of the older and newer bps), or one whose mint
     bytes cannot be read (fails closed).
   - Every other outcome is recorded and the candidate continues on the unchanged entry path.
7. **Record.** Each handled candidate gets one `observations(kind='honeypot_sim')` row, skipped ones included.
   - The bytes are the JSON record: outcome, why, scope, attempts, holder, amount, `err`, a logs excerpt, units, calls,
     `signed=false`, `sent=false`.
   - The meta carries `decision_ts`, the time the outcome was decided. All evidence was fetched before it.
   - Health has a `honeypot_sim` block (null when the filter is off).

## Why each outcome maps the way it does
| Simulation result | Outcome | Reason |
|---|---|---|
| `err: null` | `SELL_SIM_OK` | A real holder's sell executes against the current bank. |
| The token program fails inside the **swap** instruction with a code outside the benign set {0 NotRentExempt, 1 InsufficientFunds, 2 InvalidMint, 3 MintMismatch, 4 OwnerMismatch, 9 Uninitialized, 12 InvalidInstruction, 18 DecimalsMismatch} | `BLOCKED` | The token itself refused the transfer: frozen (17), non-transferable, paused, a hook-account mismatch, and so on. The benign codes are plumbing or balance problems that say nothing about the token's transfer rules. |
| The innermost failing program was invoked **by** a token program | `BLOCKED` (`TRANSFER_HOOK_REJECTED:<program>`) | This is the shape of a Token-2022 transfer hook rejecting an outbound transfer. The origin is the first `Program X failed` line, because callers fail after it. The parent comes from the invoke stack. |
| A `Program log:` line says the account is frozen, or code 17 | `BLOCKED` (`ACCOUNT_FROZEN`) | A frozen holder cannot sell. Default-frozen accounts are a classic honeypot. |
| `InsufficientFundsForFee`, `InsufficientFundsForRent`, `AccountNotFound`, `InvalidAccountForFee`, `BlockhashNotFound`; token code 1 (the holder's balance moved); Jupiter's funded-taker codes | retry once with the **next** holder, then `INCONCLUSIVE` | These are about the borrowed payer, not the token. One retry bounds the cost. |
| A failure in a non-swap instruction (setup or ATA creation), the swap failing in the AMM or router (slippage), a generic token-program error, an RPC or transport failure, a malformed answer, the hourly cap, no eligible holder, an internal error | `INCONCLUSIVE` | None of these is evidence about the token's transfer rules. |
| Jupiter answers but cannot build: a 4xx or its own `errorCode`, `outAmount 0` (`QUOTE_INVALID`), or an uncompilable build | `NO_BUILD` | No sell route exists, or the sell yields nothing (the 99–100 % transfer-fee case). A transient build failure (429, 5xx, timeout) is `INCONCLUSIVE`, never `NO_BUILD`. |

`INCONCLUSIVE` and `NO_BUILD` reject only risky mints. For a plain mint they are only recorded, so one provider hiccup cannot
starve entries. For a mint whose static extensions already make a honeypot plausible, an unverified sell fails closed.

## Budget
Worst case for one simulated candidate:
- Helius: at most 5 calls (1 `getTokenLargestAccounts`, only when the screen did not keep the holders; 1 `getMultipleAccounts`;
  up to 3 simulations).
- Jupiter: at most 3 calls (2 small builds and 1 full-size build).

The hard cap is `max_per_hour` simulated candidates (default 30, so at most 150 Helius and 90 Jupiter calls per hour). It is
persisted: on start, the `honeypot_sim` observations of the last hour are counted. Over the cap the outcome is `INCONCLUSIVE`
(`HOURLY_CAP`) and no call is made. Skipped candidates cost nothing. **With the current screen (profile 2), every pump candidate
that passes is either plain SPL (skipped) or a metadata-only Token-2022 mint (simulated).** The exit loop never calls the filter:
the only call site is `_handle_candidate`.

## Config
`honeypot_sim` (strict; unknown keys are refused):
- `enabled`: default false. Absent key or `{}` = off. The shipped example sets it to true.
- `max_per_hour`: integer 1..3600, default 30.
- `full_size`: bool, default true.

## Limitations
- **Not verified live.** The build shape is the repo's captured `/swap/v2/build` response (`addressesByLookupTableAddress`,
  instruction lists). If live builds differ, compilation fails and the outcome is `NO_BUILD`, which rejects only risky mints. The
  coordinator should run one live `--once` on a known Token-2022 mint and check the observation.
- **Whether Jupiter builds for an arbitrary taker it has not seen is untested.** Funded-taker error codes retry once.
- **The simulation sees what happens now, not later.** A hook whose rule changes after our entry (time-delayed, allow-list
  flips) passes.
- A blocklist that targets only new buyers (our future wallet) and spares existing holders passes. The holder we borrow is an
  incumbent.
- **A 99–100 % transfer fee does not make a simulated sell fail.** It is caught through the build (zero output) or the static
  risky rule, not the simulation. A successful simulation does not prove the proceeds are fair: post balances are not requested.
- Classification relies on agave's log format (`Program X invoke [n]` / `failed:`). When the logs are truncated (`Log truncated`)
  and the failing program cannot be identified, the outcome is `INCONCLUSIVE`, unless a "frozen" program-log line survived.
- **The ALT contents come from Jupiter's build response and are not checked against the chain** (the desk's `compile_unsigned`
  checks them; doing that here would cost another call). A wrong table makes the simulation fail with a generic error, which
  maps to `INCONCLUSIVE`. It never produces a false `OK`.
- Retries of the same candidate (for example a transient buy-quote failure after the simulation) and watchlist re-screens
  simulate again. The hourly cap bounds this. There is no per-mint cache.
- With today's screen profile 2, any Token-2022 mint with a hook or fee is already rejected statically. The risky rule is
  defence in depth for a wider profile or other sources.
