# T27G — Shadow strategies: last fixes (from the T27F review)

Branch `cloud/T27G`, BASE `origin/integration/r1` (T27F merged). Files: `tools/research/shadow_strategies.py`, `tests/test_shadow_strategies.py`
(plus this report). Nothing under `desk/` or `tools/research/counterfactual.py` changed (no runtime-hash impact); no provider access, no ledger
writes (parity opens ledgers read-only).

## What changed
1. **Receipt classes stay separate.** `load_outcomes` no longer drops `detail`. New `outcome_group(payload, ...)`: a REJECTED result whose detail is
   `TERMINAL_RECEIPT_UNVERIFIED` is grouped `REJECTED:<stage>:<code>:UNVERIFIED` (only a terminal receipt nobody re-verified), a verified rejection keeps
   `REJECTED:<stage>:<code>`, and `UNRESOLVED:<code>` (a latch, never a filter rejection) keeps its own group. Primary code only, as before, so a trade
   lands in exactly one group.
3. **Provisional results.** A `NOT_DISPATCHED` result, or a decision-store rejection, while the dispatch window is still open (the same rule as T26F's
   `_is_final`: strictly after `migrated_at + WINDOW_MAX_SECONDS + grace`) is grouped `...:PROVISIONAL`; it is never merged into the final
   `NOT_DISPATCHED` group because a later journal result or ledger BUY can still outrank it. Typed journal rejections and BUYs are final immediately.
   `load_outcomes(store, now=None)` takes an explicit clock (default wall clock).
2. **Non-circular parity.** The old `--parity-ledger` replays the recorded EVENTS (with their recorded evidence) through the same engine function, which
   proves determinism only. New `parity_from_samples(ledger, overrides=None)` / `--parity-samples LEDGER`: for every mint, `rebuild_candidate` builds a
   candidate from the RECORDED reserves and timestamps only (exact raw units, otherwise `ShadowError`), the assumptions come from the first recorded event
   (decimals from its token evidence, supply from market cap / price, `sol_usd`, pool fee; `max_intra_marks = 0`), and the shadow's own `simulate` with the
   ledger's saved config (`build_config(saved_cfg, {})`) decides entry and exit on SYNTHETIC events with the NEUTRAL features. Its first entry and its final
   exit (timestamp + reason) and the round-trip PnL (ladder rungs included) are compared with what the live engine recorded. Each mint is
   `MATCH`, `GAP_FEATURES` (lists every recorded feature that differs from the neutral one, with both values), `GAP_PORTFOLIO_OR_CONTROL` (a recorded
   `ENTRY_PAUSED`/`EXIT_ONLY`/`MAX_POSITIONS`/`COOLDOWN`/`ENTRY_THROTTLE`/`STALE_PORTFOLIO` rejection, or an operator control at or before the mint's
   last event), `WHAT_IF` (an override changed the config on purpose) or `UNEXPLAINED` (a divergence with no known cause: CLI exit 3). The output prints the
   neutral features and a plain statement of the expected gap.

## Limitations (honest)
- The shadow models one candidate at a time with neutral features: a mint recorded with real features, controls or portfolio effects reports a labelled gap, not a match.
  MATCH proves the reserves-to-decisions chain (sizing, ladder, stop, fees) only when the recorded features equal the neutral ones.
- Assumptions are derived from the FIRST recorded event of a mint (sol_usd, fee, supply, decimals); a ledger whose market cap or fee changes mid-path would show a gap
  the report cannot attribute beyond "UNEXPLAINED".
- Only the first entry and its final exit per mint are compared (`later_entries` is counted); strict-mode ledgers only (quote-mode needs recorded quotes).
- `docs/research/SHADOW.md` (not an owned file) does not yet describe `--parity-samples` or the `:UNVERIFIED`/`:PROVISIONAL` group suffixes; the module docstring does.
