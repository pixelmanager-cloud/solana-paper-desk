# L14 — More candidate sources + watchlist re-evaluation

Branch `cloud/L14`, BASE `origin/cloud/L09`. Paper only; nothing here signs, sends or calls a provider by itself.

## What was built
- `lean/sources.py`
  - `Source.iter_new(cursor) -> (candidates, next_cursor)`.
  - `PumpGraduationSource` wraps `lean.candidates.scan_new` for the discovery database (output identical, tested).
  - `build_sources` (strict config) and `SourceSet`: one forward-only cursor file per source (`cursor-<name>.json`), a mint handled once across sources, a failing source is isolated (`SOURCE_FAILED`, `SOURCE_CURSOR_INVALID`, `DISCOVERY_UNAVAILABLE`). A corrupt cursor skips the source and is never reset.
  - `funnel_by_source(store)`: candidates → screened → passed → entered, final rejection reasons, watch added / re-screens / ended-by-reason / entered-after-watch, per source.
- `lean/watchlist.py`
  - Allow-list of SOFT reasons (screen: `TOO_YOUNG`, `MARKET_CAP_BELOW_MIN`, `MARKET_CAP_ABOVE_MAX`, `LIQUIDITY_BELOW_MIN`; entry: `MARKET_CAP`, `LIQUIDITY`, `COST_BUDGET`, `BELOW_MINIMUM`, `MAX_POSITIONS`, `COOLDOWN`, `ENTRY_THROTTLE`, `LOSS_STREAK_PAUSE`, `DAILY_LOSS_STOP`).
  - A rejection is soft only if EVERY reason is soft. Anything else is a hazard and is never re-screened (an unknown or new reason code can only make a candidate less likely to be re-screened).
  - A watched mint is re-screened every `watch_interval_s` for `watch_hours`, at most `watch_max_per_pass` per pass. The same screen and entry decision run again, with nothing relaxed.
  - A hazard on a re-screen ends the watch (`HAZARD`), an entry ends it (`ENTERED`), the window ends it (`EXPIRED`).
  - State is append-only store events (`watch_add`, `watch_rescreen`, `watch_end`), rebuilt at start; the 6 h window does not restart.
- Runner hook (`# --- L14 hook ---`, ~40 lines): extra-source polling and re-screens run before the pump scan, bounded; `_source_of` puts `source` into each candidate row's `meta`; `_isolated` calls `watch.after_handle`.
- `lean/__main__.py`: config keys `sources` (default `[]`) and `watchlist` (default off), validated at load. `lean.example.json` lists both, with the watchlist **disabled** (see coordinator notes).

## New pools: what was NOT built, and why
Raydium CPMM, Raydium AMM v4, Meteora DAMM and DLMM are TODO. The repository has no captured account for any of them (only Jupiter route labels), and cloud workers may not call a provider, so a decoder would be unverified. Independent of the decoder, `lean.candidates.screen` and `lean.adapters.mark` only understand the PumpSwap layout. The steps to add one, and the Helius cost estimate (`120 polls/hour + one getTransaction per new signature`, per program at a 30 s poll), are in the `lean/sources.py` docstring. `build_sources` refuses those types with `SOURCE_TYPE_UNSUPPORTED`.

## Limitations
- Only the pump graduation source exists. The watchlist is only as good as the pump screen.
- The default screen `max_age_seconds` is 7200, so a watched candidate older than that ends as a hazard (`TOO_OLD` is not soft). The effective watch is therefore about 2 h unless `max_age_seconds` is raised; `watch_hours` 6 alone does not extend it.
- Re-screens use the main provider lane (not a low-priority lane); `watch_max_per_pass` (5) bounds the load. After a restart every watched mint is due at once, still limited to 5 per pass.
- A re-screen writes a new `screen` (and maybe `entry`) decision row. Existing consumers that take the latest decision per mint are right; `lean.report` is unchanged and counts first/last screens as before.
- The soft sets are a judgement. `LOSS_STREAK_PAUSE` and `DAILY_LOSS_STOP` are soft because the portfolio recovers; a quote-staleness blocker is deliberately a hazard (fail closed).
- Extra sources run before the pump scan in each pass. If two sources list the same mint, whichever frame the runner saw first labels it.
