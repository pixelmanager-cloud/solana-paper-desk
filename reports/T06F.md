## What changed (per finding)
1. **Immutable opens.** `_connect` uses `immutable=1` only when header bytes 18/19 are both 2 (WAL)
   *and* there is no sidecar content (`_is_wal` + `_quiesced`). Everything else, including the live
   rollback-journal stores `provider-pacing.sqlite`, the dispatcher journals and `evidence.sqlite`, uses plain `mode=ro`.
2. **Monitoring budget store.** `paper_monitoring_*` are now read from `evidence.sqlite` (the EvidenceStore),
   not `research.sqlite`. The `--research` option and `research=` parameter are removed (they only pointed at the wrong store).
   Fixtures use the real `EvidenceStore`, `MonitoringBudget.provision()` (real DDL + immutability triggers),
   `HistoryProgress` (real `ownership_budgets`), `provider_pacing.initialize` and the dispatcher's own `SCHEMAS`.
3. **`--allow-progress` exact prefix.** `snapshot(..., anchor=earlier_snapshot)` / `snapshot --anchor-from earlier.json`
   records the row digest at each exact old row count (ledger events/outcomes, monitoring reservations/outcomes,
   dispatcher journal tables). `compare --allow-progress` requires the digest at the exact old count and **fails
   closed** if the later snapshot has none ("retake the later snapshot with --anchor-from"); the old nearest-stride-mark
   fallback is gone. A >20k-row test rewrites the last old row.
4. **Concurrency tests.** Known-answer tests from the real engine for buy A, buy B, sell B, sell A (cost, proceeds,
   PnL, closing order, interleaved timestamps, cash/realized) and for a 3-rung take-profit ladder + final exit (4 partial sells),
   plus a mid-sequence open-leg case and a duplicate-entry-into-open-mint rejection.
5. **Per-sell PnL.** Each sell's `proceeds - realized_pnl` must equal `cost_left * qty / qty_held` (the engine's own
   release rule). Moving PnL between two sells of one position leaves every aggregate unchanged and is now rejected.
6. **Volatile pacing fields.** `next_at`, `blocked_until`, `pending`, waiter count live in a separate `pacing_volatile`
   section, excluded from strict equality, and reported under `volatile` in the compare result. `pacing` keeps only
   `[provider, high_water]`; high-water may rise (other services share the store) but never fall or disappear, in strict and progress modes.
7. **Duplicate-fill key** is the tuple `(event_id, side, mint)`. Test: `('E','buy','sellM')` and `('Ebuy','sell','M')` collided under concatenation.

## Remaining limitations
- `MonitoringBudget.provision()` binds to a quote-mode ledger checkpoint; the constant-product fixture ledger is not one, so
  tests stub only `MonitoringBudget._checkpoint`. The DDL, triggers and columns under test are the production ones.
  Reservations are inserted by SQL (the real `reserve_read` needs a held quote-mode position + history progress).
- Monitoring and ownership are read in two separate read transactions of `evidence.sqlite`; they are not cross-checked against each other.
- Anchors prove the old prefix only for tables present in the anchor snapshot; a table first appearing in the later snapshot has no old prefix to prove.
- Fills carry no on-chain proof; everything stays `EXECUTION_UNVERIFIED`.

## For the coordinator
- **CLI change:** `snapshot` no longer accepts `--research`; add `--anchor-from <snapA.json>` when taking snapshot B for
  `compare --allow-progress`. Without it `--allow-progress` fails closed whenever new rows exist. A strict cold-restart
  compare (no new activity) needs no anchor. `docs/ops/RUNBOOK.md` (T11) should use these flags.
- Snapshot JSON gained `pacing_volatile`, `pacing.providers` is now `[provider, high_water]`; snapshots from the T06 tip
  are not comparable with these (different shape) — retake both.
- No deploy, migration or production-store impact; read-only tool outside the `desk/` hash domain.
