# L06F — attribution by the ENTRY strategy_version (report + notifier)

Branch `cloud/L06F`, BASE `origin/integration/r1`. `desk/` untouched. PAPER ONLY.

## Problem and what I found
A position bought under `lean-1-collect` was sold after a restart under `lean-1-collect-b`, and the sell fill carries the new version. Reading the code first:
- **`lean.report`** already built each TRADE from its opening buy (`trades()` takes the version of the first fill of the lifecycle), so the per-trade table and `pnl_by_strategy` were not split. What was missing was visibility and a guard: nothing flagged a trade whose fills span versions, and no test locked the rule in.
- **`lean.notify`** WAS wrong in three places: `/pnl` summed each sell's `realized_lamports` under the SELL fill's version; `StoreView.closed()` used the version of the `closed` position_state row (the closing sell's); and a SELL message printed the sell's version as the strategy.

## Changes
- `lean/report.py`: every trade records the set of versions of its fills; `trade_row` gets `mixed_version` (1/0) and `fill_versions`; `pnl_by_strategy` gets `mixed_version_trades` per strategy; the HTML shows the new columns and says "by the version of the OPENING buy".
- `lean/notify.py`:
  - `StoreView.closed()` returns the OPENING buy's `strategy_version` plus `mixed_version`.
  - New `StoreView.realized_by_opening_version()`: one SQL join (sell fill -> its `rung`/`closed` position_state row -> the opening fill). `/pnl` uses it, so the whole trade, including a rung sold under A and the rest under B, is counted under A. A sell without a lifecycle row (a legacy store) keeps its own version, so nothing is dropped.
  - `fill_event`: for a SELL, `strategy_version` is the opening buy's and `mixed_version` says whether the sell carried another version.
- Tests: `tests/lean/test_attribution.py` (new, 6, REAL lean store: report and notifier) and `MixedVersions` in `tests/lean/test_report.py` (2, generic layout).

## Tests
- `python -m unittest discover -s tests/lean -t .` in one process => 339 tests, OK, rc=0.
- Fail-first: against the BASE `report.py` / `notify.py` the 8 new tests give 2 failures + 5 errors (RED); GREEN with the change.
- Mutations (each RED, restored): `closed()` takes the closing row's version; `/pnl` groups by the sell's own version; the SELL message keeps the sell's version; the report re-labels a trade by its LAST fill; `mixed_version` forced to 0.

## Limitations
- A trade is attributed to its opening buy; a position that is added to later under another version stays with the first one by design.
- The daily summary and `/status`/`/today` are not per-version and are unchanged (only `/pnl`, the closed-trade rows and the sell message are version-aware).
- `mixed_version` is only a flag; no PnL is split or re-allocated between versions.
