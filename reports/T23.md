## F5 — `desk/engine.py` (opt-in, versioned)
- New config key `paper_exit_only_recovery_version: 1` (any other value → `ValueError`). Absent = byte-identical behavior to BASE (verified by test; the only default-path addition is a `pop` of a key that never exists).
- When the engine itself pauses for an unresolved exit (`risk()` branch and clock branch) it records `state["exit_only_cause"]="UNRESOLVED_EXIT"` (flag on only). `risk()` returns EXIT_ONLY → RUNNING only if that cause is present AND no position has `exit_blocked`; then it re-evaluates normally, so daily liquidation, daily pause, loss-streak pause and a still-blocked second position all still apply (control `UNRESOLVED_EXIT_CLEARED` is emitted only when it really lifts).
- Operator commands pop the cause (operator authority replaces the engine pause); operator `EXIT_ONLY`, `PAUSE_ENTRY`, `LIQUIDATE`, STOPPED are never lifted. `RESUME` cannot bypass a still-blocked exit.
- State key is additive: `ledger.py`/`paper_checkpoint.py` validate `required <= keys`, so no edit was needed there (independent review found no key-set/hash comparison elsewhere).

## F6 — `desk/provider_pacing.py`
- Owner liveness = kernel `flock` on `<db>.holder-<provider>.lock`, taken right after a grant and held until `finish`/`throttle` (released BEFORE the commit so a new grantee always finds it free; any live Pacer in the process may acknowledge a ticket). SIGKILL/crash/GC of the owner releases it; a discarded Pacer counts as gone.
- A pending grant is reclaimed inside the acquirer's write transaction only if age (`now - (next_at - cadence)`) ≥ `max(60 s, 30 × cadence)` AND the holder lock can be taken (owner provably gone) AND fewer than `MAX_RECLAIMS` (10000) rows exist. Otherwise `PACING_OUTCOME_PENDING` exactly as before.
- Effect: `pending=NULL`, `blocked_until=MAX(blocked_until, now+backoff)` (unknown outcome treated as a throttle with no Retry-After, fixed 30 s backoff starting at reclaim), `high_water` updated; `next_at`, cadence and policy untouched (the Kraken 2.0 s lane is never altered). One append-only row in new table `pacing_reclaims` (created lazily at first reclaim; UPDATE/DELETE trigger-guarded; unique per ticket); `Pacer._validate` accepts exactly that schema (+ `sqlite_sequence`) and rejects tampering.
- If the holder lock cannot be taken at grant time, the unused grant is acknowledged and `PACING_HOLDER_LOCK_UNAVAILABLE` is raised (fail closed; no unprotected ticket).

## Limitations (honest)
- **Mixed old/new code on one pacing DB breaks at the first reclaim:** after it the DB has `pacing_reclaims`/`sqlite_sequence`, and OLD code's `Pacer()` constructor raises `PACING_DATABASE_INVALID` (also `tools/verify_http403_originals.py`, `tools/verify_kraken_successor_originals.py` compare live schema strictly). Deploy new code to every service before relying on reclaim.
- A new-code owner is protected by its flock; an OLD-code owner has no lock, so a >60 s old grant held by old code would look "gone". Requests are bounded far below 60 s; still, don't mix versions.
- Lock identity is the path string (bind-mount/alias gives a different lock file); hard links are already rejected by the pacer.
- Reclaim clears an unknown outcome without a request charge (nothing to charge; the original charge stays), under a 30 s embargo from reclaim time — not a longer Retry-After the dead request may have received.
- F5: a daily-drawdown breach that occurred while an exit was blocked and has recovered by the time the exit clears is not remembered (base would stay EXIT_ONLY forever); loss-streak/liquidation/current drawdown still hold. A partial sell that re-blocks within the same event could emit CLEARED then BLOCKS (read from code, not exercised; end state is EXIT_ONLY either way).
- Not verified against a real service restart on the VPS; no live access.
