## What changed

### 1. Transient held-read failures no longer latch (still charged and retained)
`monitoring_budget.TRANSIENT_FAILURE_CODES` now covers: `TRANSPORT_ERROR`, `DEADLINE_EXCEEDED`,
`RPC_ERROR`, `KRAKEN_PROVIDER_ERROR`, `PACING_DEADLINE_EXCEEDED`, `PACING_DATABASE_BUSY`,
`PACING_QUEUE_FULL`, `ABANDONED_CHARGED`. `HTTP_REJECTED` is transient for status `None`
(`CoordinatorRPCError`), 408, 429 and 5xx; 401/403/400/404/3xx and every other code latch.

| failure_code | latches |
|---|---|
| TRANSPORT_ERROR (known network exception), DEADLINE_EXCEEDED, RPC_ERROR, KRAKEN_PROVIDER_ERROR, PACING_DEADLINE_EXCEEDED / _DATABASE_BUSY / _QUEUE_FULL, ABANDONED_CHARGED | no |
| HTTP_REJECTED with status None / 408 / 429 / 5xx | no |
| HTTP_REJECTED 400/401/403/404/other | yes |
| RESPONSE_INVALID / _TRUNCATED / _OVERSIZED / _HEADERS_INVALID, CLOCK_INVALID, CREDENTIAL_UNAVAILABLE, KRAKEN_PRICE_INVALID, KRAKEN_PACING_NOT_CONFIGURED | yes |
| PACING_DATABASE_INVALID / _CHANGED, PACING_GRANT_MISMATCH, PACING_POLICY_INVALID, PACING_CLOCK_INVALID, PACING_REQUEST_INVALID, any unknown code | yes |
| TLS_ERROR (new), UNCLASSIFIED_ERROR (new) | yes |

`OUTCOME_PERSISTENCE_FAILED` is raised without an attempt record, so it never reaches the predicate.

### 2. The catch-all is no longer silent
`paper_read_sources.classify_exception` runs only when the failing stage is network I/O
(`code == 'TRANSPORT_ERROR'`). `TRANSPORT_ERROR` is returned only for timeouts, `ConnectionError`
(reset/refused/aborted, `RemoteDisconnected`), `socket.gaierror`/`herror`, OSErrors with
ENETUNREACH/EHOSTUNREACH/ENETDOWN/EHOSTDOWN/ETIMEDOUT/ECONNRESET/ECONNREFUSED/ECONNABORTED/EPIPE and a TLS
connection closed by the peer (`SSLEOFError`, `SSLZeroReturnError`). `URLError` is unwrapped to its `reason`.
Any other `ssl.SSLError` (incl. certificate verification) is `TLS_ERROR`; everything else (ValueError, AttributeError,
KeyError, RuntimeError, a bare `OSError`, `PermissionError`, a `URLError` that only carries a message,
`BadStatusLine`) is `UNCLASSIFIED_ERROR`. Both latch. Exception text is never retained (test asserts a sentinel is absent).

### 3. `MONITORING_OUTCOME_PENDING` after a kill is resolved, append-only
- A reservation with no outcome is abandonable only when **all** hold: allowance version is not the handoff
  context (3); `now - reserved_at > ABANDON_AFTER_SECONDS` (60 s; a provider call is bounded to 15 s); and
  `_owner_gone()`: no process other than the current one holds a flock on `<evidence>.ownership-invocation.lock`
  or `<ledger>.paper-cycle.lock`. Holders come from `/proc/locks` (the kernel releases a flock when its process
  dies, so this is the lease/PID evidence); an unreadable lock table is treated as "not provable" and keeps
  failing closed. The lock is only read, never probed, so a live owner never sees spurious "busy".
- `reserve_read` then appends one outcome per orphan inside its own `BEGIN IMMEDIATE` transaction: an evidence page
  `paper_monitoring_abandoned_v1` with `failure_code='ABANDONED_CHARGED'`, `charged=true`, `refunded=false`, the reservation
  receipt rebuilt from the reservation row, and the outcome row. The reservation row, `total`, window usage and cap are
  unchanged: the request stays charged and counted. The record is validated with the same predicates `_accounting`
  applies (new `_receipt_valid` / `_outcome_bound`, factored out of `_accounting`) before anything is written.
- `_accounting` accepts the abandoned record only when its exact field set, scan/method/params-hash binding,
  reservation id, `reserved_at`, `charged`/`refunded` flags and `resolved_at > reserved_at + deadline` all match, so a
  forged early resolution, a refund, an uncharged request or another reservation's receipt fails verification.
- `snapshot()` stays read-only: it just stops reporting a resolvable orphan as a blocker (`status AVAILABLE`); the next
  read appends the outcome. The T09 `expectedFailure` is un-marked and passes.

## Remaining limitations
- Abandonment is not implemented for the monitoring handoff context (allowance version 3): its receipts must carry
  context hashes. Such a store keeps failing closed (`MONITORING_OUTCOME_PENDING`) exactly as before. Fresh-start stores
  are version 1 -> 2 (upgraded allowance), which is supported and tested for version 1; version 2 is covered by the
  shared receipt code path (`policy_hash`, cap) but not by a dedicated abandonment test.
- Needs Linux `/proc/locks`. If it is unreadable, or lists the lock with an unparseable pid, the orphan is never resolved
  (fail closed). pid translation across PID namespaces can show a foreign holder as another pid: also fail closed.
- For up to 60 s after a kill, a held pass fails with `MONITORING_OUTCOME_PENDING` (no exit can run in that window).
- The global terminal gate (`paper_terminal_reconciliation`, T01/T22 files, not edited) still raises "Monitoring transport
  unresolved" while a pending row exists, so an entry is refused until the next held read appends the abandoned outcome.
  This cannot strand an entry: the pending row only exists while the position is open, and held passes resolve it.
- `RPC_ERROR` is now never latching. A permanently invalid request would burn the (bounded, charged) allowance instead of
  halting it; the cap still bounds this.
- `snapshot()` remains O(history) (T24 scope; its `expectedFailure` is untouched).

## For the coordinator
- **Hash domain:** both edited files are under `desk/`, so the implementation hash changes. Per the fresh-start policy,
  deploy on a flat ledger by rotating to a new store set; no successor pin is created or needed for new stores.
- **No schema or store change.** New evidence record kind `paper_monitoring_abandoned_v1` and three new failure codes
  (`TLS_ERROR`, `UNCLASSIFIED_ERROR`, `ABANDONED_CHARGED`). Old stores without orphans are unaffected; an old store with a
  pending orphan gets one append-only outcome on its next held read (never a refund/reset).
- Decision made: 60 s deadline + lock lease (conservative default; the lease is the real safety, the age a margin).
  Raise `ABANDON_AFTER_SECONDS` if you prefer a longer blind window over trusting the lease.
- Operator visibility: a `TLS_ERROR` or `UNCLASSIFIED_ERROR` latch is a bug or a MITM symptom, not an outage; it needs a human.
