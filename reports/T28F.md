## Findings -> changes (all in `tools/ops/held_watcher.py` unless noted)
1. **(HIGH) Trigger budgets.** Reasons are classed `price` (STOP, TRAILING_STOP, TAKE_PROFIT) or `time` (MAX_HOLD, TIME_STOP, LIQUIDATE) and recorded in a new `triggers.klass` column. Each class has its own per-position and global hourly caps (price 12/60 as before, time 6/30), so an unresolvable MAX_HOLD cannot exhaust the price budget. A price exit may always fire once per `--price-guarantee-seconds` (60) regardless of caps. A time/mode reason the held pass already handled (the ledger journaled an event for that mint after our request while the position is still open) is no longer re-fired at the same pace: the debounce doubles each time (30, 60, 120 ... capped at 1 h).
2. **(HIGH) Same-slot reserves.** Balances are buffered per slot and only a COMPLETE pair of one slot becomes a snapshot that can be priced; a lone vault update waits `--settle-seconds` (1 s) and is then completed by one same-slot poll. Polling groups both vaults of a pool in the same `getMultipleAccounts` call (never split across the 100-account chunks). A liquidity add that doubles both reserves no longer looks like a 50% crash.
3. **(MED) Provider backoff.** HTTP 429/5xx, timeouts and network errors hold ALL requests with exponential jittered backoff (2, 4, 8 s ... capped by `--http-backoff-cap`, default 300), nothing sent or charged while held, reset on success (`PROVIDER_BACKOFF`, status DEGRADED). Defaults are now 0.5 req/s (`--min-request-interval 2.0`) and 1800 requests/hour. The shared-pacing rationale (T09 F6) and the starvation guard are documented in `docs/ops/HELD_WATCHER.md` (and asserted by a test).
4. **(MED) Lost triggers.** After a successful request the watcher asks again after 5, 10, 20 s (max 3 refires, `source=refire`, counted in the budgets) unless a held-pass event for that mint appears in the ledger, then reports `TRIGGER_NOT_ACKNOWLEDGED`. A vanished reason cancels the refire.
5. **(MED) Latency attribution.** `latency` pairs a trigger only with the first held-pass event / sell fill whose second is strictly after the trigger and within 300 s; several requests that lead to one pass attribute the latency once, to the LAST request (the rest are `superseded`). The slot of each trigger is resolved with `getBlockTime` in the background (charged to the allowance, retried twice, appended to `trigger_slot_times`) so `slot_to_trigger_seconds` is real when available.
6. **(LOW) Stream health.** A connected but silent stream (`--stall-seconds`, 60) is verified by a poll: unchanged reserves = quiet pool; changed reserves = lost notifications -> `STREAM_STALLED`, polling takes over and a fresh connection is made. The reconnect backoff persists across connects and resets only after `--stable-seconds` (60) of stable connection.
7. **(LOW) Write scope.** `deploy/fresh/desk-held-watcher.service`: `ReadWritePaths=<STATE_DIR>/held-watcher` only (a test asserts it is the sole writable path and equals `--state-dir`).
8. **(LOW) Mark accuracy.** Pool fee + PumpSwap creator fee (operator `--creator-fee-bps` plus the pool account's own override), Token-2022 `TransferFeeConfig` (newer schedule, max ignored) and virtual quote reserves are in the mark; pool and mint facts are read once per new pool and cached in `vaults.extra`. A position without `quote_execution` raises `POSITION_NO_QUOTE_EXECUTION` and is priced with the mint's decimals; if those are unknown it raises `POSITION_NO_DECIMALS` (DEGRADED). Price triggers are never dropped silently. Remaining assumptions are listed in the doc (global PumpSwap fee tier not read, epoch of the transfer fee not checked).
9. **(LOW) Trailing peak.** The line follows the engine's RECORDED peak (raised to the current ratio); the watcher's own higher peak moves it by at most one margin.

## Remaining limitations (honest)
- The mark is still an estimate; the held pass may find a different executable quote. DANGER exits remain timer-only.
- `getBlockTime` can fail for a just-confirmed slot; failed attempts are recorded and capped at three. Latency before block time is known is only the local receive time.
- A same-slot pair needs both vaults to change in a slot or one settle poll; a one-vault-only change costs up to `--settle-seconds` plus one poll.
- Time-class backoff relies on journaled events for the mint; a held pass that crashes before journaling looks like "not handled" and is refired (bounded by the refire and cap limits).
- Real websocket, real Helius responses and a real systemd path unit were not exercised (fakes only), as in T28.
