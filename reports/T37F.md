## Items
1. **(HIGH) A provider failure must not latch.** Two causes, both fixed:
   * R1's allow-list (T22F) did not know the v2 codes, so even `USD_SOURCE_DIVERGENCE` had silently stopped being a retired no-entry
     (it fell through to a FAILED_CHARGED closure). `usd_valuation.NORMAL_BLOCKERS = {USD_SOURCE_DIVERGENCE, SOL_USD_UNAVAILABLE}` is now
     part of `paper_cycle_no_entry.producer_blocker_is_normal` (one line), so the no-entry publication and T22G's closure accept them.
     They are valuation-only facts about a provider, produced by our own code from verified retained originals; no other `SOL_USD*`
     code is accepted (`SOL_USD_TRUSTED_INPUT_INVALID`, `...BLOCK_TIME_MISSING` stay integrity).
   * The no-entry proof refused any failed charged attempt. It now accepts a failed attempt iff the result CITES it in
     `usd_evidence_refs` and it is a SOL/USD attempt (Jupiter PriceV3 or Kraken) of THIS scan (`_cited_usd_failure`). The two committed
     latch tests are flipped: the entry ends as a proper terminal `NO_ENTRY` row citing both failed attempts (charges retained at 7,
     scan retired, gate clean); the exit ends `FAILED_CHARGED` (T22G), the position stays held, the monitoring allowance is not
     latched and the next pass with a healthy provider sells.
   * Found on the way (T22F regression, fixed here): R2's per-scan index took the attempt refs from the result, but the in-cycle
     history pager keeps its own refs, so any no-entry pass that charged a history page inside the cycle was refused at publication
     (masked by the closure fallback). `publish` now looks up only the missing charge numbers among the NEWEST 2048 pages
     (bounded, flat in store size). Production `history_first` prepares history in its own pass and was not affected.
2. **(MED) Regime producer source and Kraken schedule.** Under v2 the regime reads the PRIMARY (Jupiter PriceV3) series from the retained
   originals (strictly parsed, judged at their own acquisition second) and uses the Kraken series only when the primary has too little
   span; a series never mixes the two sources, so a failed or divergent cross-check cannot move it. `regime_producer.evidence(...,
   valuation_version=2)`; v0/v1 callers are untouched (Kraken only, the cycle passes the keyword only for v2). Kraken is now fetched on an
   entry only when no Kraken attempt (success or failure) was acquired within `usd_cross_check_seconds` (default 300, integer 1..3600,
   the loader requires positive numbers), plus whenever the primary is unusable (fallback). A skipped cross-check is recorded exactly
   like a failed one (primary only, `fallback: null`). Example config carries the key.
3. **(MED) Byte identity.** `tests/test_usd_valuation_identity.py`: with the flag absent (v0) and with version 1, the scripted entry ->
   held mark -> exit lifecycle (wall clock frozen, `uuid4` a counter) writes `events`/`outcomes` bytes whose sha256 equal GOLDEN digests
   that I produced on `origin/cloud/T22G` (before any USD v2 code) and reproduced on this branch (identical).
4. **(LOW) Divergence limit.** `model.validate_event(..., usd_divergence=None)`: when the caller has the configured limit the saved
   valuation is rebuilt with it and an event whose stored limit differs is refused. `engine.transition` now passes it (`_usd_limit`,
   v2 only). Callers without a config keep the previous behaviour; the cfg-bound validators (engine, checkpoint replay) were already authoritative.
5. **(LOW) Persistent auth failures.** `usd_valuation.persistent_auth_failure(evidence_db)` (bounded, read-only, never raises) and a
   `usd_auth` check in `tools/ops/healthcheck.py`: WARN when the newest 3+ Jupiter attempts were all HTTP 401/403; cleared by one
   success; 5xx and Kraken attempts do not count; never CRITICAL by itself. `parse_jupiter` refuses a response with any mint other than
   SOL (`UNEXPECTED_EXTRA_MINTS`, so the primary falls back). `ExampleConfigTests` moved above the `unittest.main()` guard (it was never run).

## Limitations
* The 5-minute schedule means the divergence guard does not run on entries whose cross-check is skipped (pinned by a test): a wrong
  primary can pass for up to `usd_cross_check_seconds`. Set a small value (min 1) to approach cross-check-every-entry.
* Any provider failure of a USD source (including 401/403, TLS and malformed answers) is an ORDINARY outcome for the valuation
  (fall back, or unavailable); only the health WARNING reports a persistently rejected key. Kraken's non-transient failures still
  latch the MONITORING allowance (T25F), unchanged. `SOL_USD_TRUSTED_INPUT_INVALID` (shape/binding of our own retained originals) still holds the pass.
* The watchlist `NOT_YET` table still does not list `USD_SOURCE_DIVERGENCE` / `SOL_USD_UNAVAILABLE` (T20 files), so a re-evaluation
  of such a candidate is classified by the existing fallbacks.
* Jupiter validity remains by acquisition time (no chain-time dating); PriceV3 policy conflict with the worker prompt ("never retry or
  special-case PriceV3") is as in T37: one call per use, never retried; the coordinator should confirm before enabling.
