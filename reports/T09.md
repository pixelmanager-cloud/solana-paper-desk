## Ranked findings

### CRITICAL
**F1. Every non-COMPLETE pass after the first charged request latches the whole store — T01 as specified fixes only the typed-rejection corner.**
- `desk/paper_cycle.py` ~:676-678 sets `outcome_hash` only for COMPLETE or zero-attempt passes. `paper_terminal_reconciliation._gate` :544-583 returns `OBSERVATION_RECOVERY_REQUIRED` for any NULL pass without a receipt, globally (not per scan/position).
- Faults that still latch after T01: `ObservationError`, `PaperReadError` (HTTP 429/5xx) escaping `run_once` (entry prep inserts the NULL pass before the first history read, `paper_history_preparation.py` ~:46), timeouts, SIGKILL mid-pass ("Monitoring transport unresolved", terminal :404).
- **Held variant (worst):** a held pass that spent monitoring requests then failed (sell quote below the 0.00005 SOL fee → `UNRESOLVED_QUOTE_DEMAND`; zero-out quote → `HELD_OBSERVATION_CONTENT_REJECTED`; any timeout) leaves a NULL pass; every later held pass is refused; the open position can never be sold even after the quote recovers.
- Tests (verified): `HeldPassLatchTests.test_dust_sell_quote_must_not_strand_position`, `...test_zero_sell_quote_must_not_strand_position` (RED); `HeldMonitoringTransientFault.test_one_transient_monitoring_read_failure_strands_open_position_forever`, `HistoryFirstTransientFault.test_transient_history_error_in_preparation_latches_whole_store`, `DispatcherTransientFault.test_single_transient_acquisition_timeout_permanently_kills_dispatcher` (RED); `HeldPassLatchTests.test_latch_is_global_not_per_scan_and_per_position` (green).
- Recommendation: T01 must classify held/monitoring failures and exceptions-after-charge too (category (a) vs (b)), not just `CycleBlocked` on entry.

**F2. Monitoring latches `SOURCE_FAILURE` / `OUTCOME_PENDING` permanently.**
- `monitoring_budget.py` ~:443/:478: any failed held read sets `blocked='SOURCE_FAILURE'`; nothing clears it; `terminal._monitoring` (:401) raises "Monitoring latch unresolved"; `CLOCK_ROLLBACK` (:354, e.g. NTP step back) is the same latch. A reservation committed before the HTTP call and killed leaves `MONITORING_OUTCOME_PENDING` with no TTL. Entries blocked (dispatcher `_preflight`) and held monitoring stopped; only a reviewed handoff (`monitoring_handoff.py:118`) recovers.
- Tests (verified): `MonitoringLatchTests.test_one_transient_failed_read_must_not_block_entries_for_good`, `...test_process_killed_after_reservation_must_not_block_forever` (RED).

**F3. Dispatcher: any failure after the intent is written is permanent.**
- `tools/paper_entry_dispatcher.py` `_write(intents)` ~:638 then `PROVIDER_RETRY_REQUIRED`/`SEED_HISTORY_UNAVAILABLE`/`BUSY`/limit statuses raise (:656-666), or a SIGKILL/`TimeoutStartSec` hits. `_check_records` :270 raises "Unresolved dispatch; no retry" on every later tick, including dry-run. Candidate 1252 was already retired this way. (Verified, see F1 dispatcher test.)

### HIGH
**F4. Fresh pacing DB cannot obtain the Kraken lane.** `config/kraken-pacing-migration.json` pins the production path, exact production `old_state` floats and a source hash; `desk/kraken_pacing_migration.py:11-16/:71-76` compare exactly. A DB from `provider_pacing.initialize()` → "Pacing migration not reviewed" → dispatcher `plan` raises, `paper_read_sources.py:228` `KRAKEN_PACING_NOT_CONFIGURED`. The pin also embeds `implementation_hash()` so any `desk/` change (T01) stales it. Workaround: reuse the migrated shared pacing DB (the plan says it is shared anyway) or re-pin after final freeze. Test (RED): `FreshPacingTests.test_fresh_pacing_db_can_receive_reviewed_kraken_migration`, `FreshStoreBootstrapTests.test_fresh_pacing_db_can_gain_kraken_lane`. **T13 must use a copy of the migrated pacing DB, never initialise a new one.**

**F5. Mode sticks at `EXIT_ONLY` after the first trade; entries stop silently forever.** `desk/engine.py` ~:342-350 sets `EXIT_ONLY` when a position has `exit_blocked`; the stale-mark watchdog does so ~10s after entry because the held timer runs every 5 min. Nothing returns to `RUNNING` except operator `--control RESUME`. Scheduler/dispatcher answer `HELD_POSITION_PRIORITY` exit 0 with no alert. Verified: entry → tick 11 s later → clean STOP exit → 0 positions, mode `EXIT_ONLY`. Test (RED): `ExitOnlyStickinessTests.test_mode_returns_to_running_after_stale_mark_exit`. (Overlaps T08 case 5/T07; route to the T08/T07 owners.)

**F6. A pacing slot orphaned by a kill blocks every provider call forever.** `provider_pacing.py` ~:165 sets `pending=ticket`; only `finish()`/`throttle()` in the same process clear it; no TTL/reaper. SIGTERM does not run `finally`. Later `acquire()` → `PACING_OUTCOME_PENDING`; dispatcher `_preflight` ~:311/:397 refuses. Docs forbid hand-clearing. Tests: `test_slot_granted_to_killed_process_is_reclaimed_eventually` (RED), `test_orphaned_pending_blocks_every_provider_call_today` (green).

**F7. Gate/replay cost grows O(R×P); hard latch past 4096 pages.** `history_preparation_rejection.py:100-122` `_attempts` decodes every `pages` row per retained rejection; `:105` raises "Preparation attempt inventory bound" at >4096 pages. Measured: 0.17 s baseline, +0.35 ms per unrelated page. Extrapolation (read, not measured): R=100, P=3000 ≈ 120 s per gate call; the dispatcher calls the gate ≥8× per dispatch (:315,:353,:392,:636). Caps: `MAX_REJECTIONS=512`, `MAX_RECEIPTS=256` (failure swallowed at paper_cycle :673), 10000 passes. Estimated 4096 pages after ~70–200 candidates (guess). Tests: `PreparationRejectionReplayGrowth.*` (RED), `RetainedCountCaps.test_original_pass_count_bound_is_a_hard_latch` (green). Interacts with T01: each new terminal-outcome row feeds this growth.

**F8. Wall timeouts in the repo conflict with the code's own budgets.** Repo units: entry `TimeoutStartSec=180` (coordinator says 600 s), held `TimeoutStartSec=20` (coordinator says 120 s). Code worst case for entry ≈ 18×15 s transport + `time.sleep(2.0)` (paper_cycle :506) + 10 s fresh cycle ≈ 282 s + pacing waits. A kill after the intent = F3. Held: 10 s `_Budget` deadline + export leaves ~10 s slack under 20 s. Tests (RED): `UnitBudgetTests.test_entry_wall_timeout_covers_code_time_budgets` (180<282), `test_held_wall_timeout_covers_cycle_plus_accounting` (20<120). **Confirm the production values; if production really has 600/120 these two are moot but the repo templates still disagree.**

**F9. 10 s whole-pass deadline vs real latency.** `_Budget.remaining` raises `CYCLE_DEADLINE_UNAVAILABLE` at start+10 s (paper_cycle ~:134); price TTL 10 s. `docs/readiness.md`: fixtures with no network latency already took 7.0 s (BUY) / 7.8 s (SELL) with 2 s pacing. ~1 s extra latency per request overruns, and by F1 each overrun latches. Test (RED, not a live measurement): `LiveLatencyDeadlineTests.test_entry_survives_realistic_provider_latency`.

**F10. Any byte change under `desk/` after ledger creation blocks everything.** `implementation_hash` (runtime_compatibility.py:19) is pinned by ledger metadata, monitoring `code_hash` (monitoring_budget.py:35), dispatcher context (`source_hash`, `tool_hash`, inodes of six files, paper_entry_dispatcher.py:147-153,309). A hotfix with an open position → `RUNTIME_IDENTITY_INVALID` / "Reviewed context changed"; edge allowlist max 8 (runtime) / 4 (monitoring). Restoring/copying a DB changes the inode and breaks the pin. Rule: freeze `desk/` and `tools/` before `initialize` and monitoring `provision`; rotate only when flat. Test (green): `PinMismatch.test_any_byte_change_under_desk_blocks_every_cycle_until_reviewed_transition`.

**F11. Deploy templates cannot produce the first cycle as written.** Held service passes `--dependency-blocker RUNTIME_REVIEW_AND_PATH_BINDINGS_REQUIRED` (exit 2, no exit attempted) and different config/ledger paths from entry (`paper-quote-reviewed.json`/`active-paper.sqlite` vs `paper-kraken-reviewed.json`/`paper-kraken-77de75a2.sqlite`; neither config is in the repo); expire unit uses `config/paper.json` (fails `cycle._config`, so the watchdog never covers the Kraken ledger — and pointing it right triggers F5); held unit sets no `DESK_PROVIDER_PACING_DB` (unpaced reads); entry unit is dry-run (no `--execute`/`--systemd-credentials`); timers have no `[Install]`. Nothing sets `DESK_PAPER_SCHEDULER_IDENTITY` or creates `paper-scheduler.lock`: `lease()` opens without `O_CREAT` and `main()` has no handler → traceback every tick. Tests: `FreshStoreBootstrapTests.test_scheduler_lease_fails_closed_without_traceback_on_fresh_dir` (RED), `..._test_scheduler_units_provide_lease_identity` (RED), `test_fresh_store_lease_requires_preexisting_lock_and_identity_env` (green). For T11/T13 owners.

### MEDIUM
**F12. Monitoring allowance on a fresh store.** `cycle.run_once` never provisions (paper_cycle :462); without `MonitoringBudget.provision()` held monitoring cannot read. Cap stays 60/hour (monitoring_budget.py:24); `upgrade_existing` to 3600/h fails on a fresh store with "no such table: ownership_acquisition_setup" (:465, the table appears only after the first acquisition). A 5-request held pass every 5 min = 60/h with zero slack; a partial exit costs 6. Test (RED): `FreshStoreBootstrapTests.test_monitoring_3600_upgrade_available_on_fresh_stores`. **T13's "monitoring 3600/hour" requirement may not be achievable via supported APIs on an empty store — verify.**

**F13. Lifetime-18 investigation budget is nearly consumed by entry.** Entry history needs `ceiling-used >= fresh(7)+1`; entry spends 7–9 history + ~7 fresh requests; past candidates used 13–14 of 18. Exit cannot be afforded from the investigation budget, so the first position is unexitable until the monitoring allowance is provisioned (F12). Read only.

**F14. Monitoring accounting cost grows with history.** `monitoring_budget._accounting` (~:215-250) loads every past reservation; a held read ≈ 5 full passes. Measured 0.073 s@50 rows, 0.136 s@400 (tiny blobs); real blobs larger, 10 s deadline plausibly reached ≈1800 rows (~25 h of continuous holding, estimate). Hourly ceilings are not the risk (≈72/h vs 3600). Test (RED): `MonitoringScalingTests.test_snapshot_cost_is_independent_of_total_history`. Memory (128/384 MB) looked fine; journal reads bounded to 32 MB.

**F15. Candidate supply.** `_select` reads only the newest 500 `raw_events` then requires age 300–7200 s; at the 5000/h discovery cap the eligible window shrinks to ~60 s. Token-2022 dominates discovery (readiness notes). Read only.
