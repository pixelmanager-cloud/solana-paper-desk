# L12F — Fix L12 (entry features), on the shared low lane

BASE: `origin/integration/r1` + `origin/cloud/L07R` (the shared LOW lane and the path recorder; not yet in integration/r1 when I started) with the old
`cloud/L12` merged in. `desk/` untouched. Paper only, read-only RPC, features only (the strategy never reads them).

## Per review item
1. **Missing fields: filled or removed.** Version 2 of the row (`FEATURES_VERSION = 2`) has only fields that can be filled inside the 3-call budget.
   - New / fixed: `top10_pct`, `top1_pct` (share of the TOTAL supply, **excluding the pool vault and the burn accounts**: the ATAs of the incinerator and
     of the system program for this mint and token program, derived, no request), `creator_wallet`, `dev_holding_pct`, `graduation_block_time`,
     `seconds_graduation_to_screen`, `tx_count_first_10m`.
   - Removed with their reason kept in `REMOVED_FIELDS` (and a test that none of them is a null column): `holder_count` (needs a full holder scan / DAS),
     buys / sells / unique buyers / buy volume (parsed transactions over the budget; L13 `wallet_signals` records unique buyers, same-slot buyers and
     snipers from the pool's first swaps), `has_twitter/telegram/website` (metadata JSON, no allowed RPC), `seconds_creation_to_graduation` (needs the
     mint's first transaction: after one page it is `HISTORY_TRUNCATED` for a graduated token, and paging is exactly what item 2 forbids).
   - **Soft rejects** (market-cap / liquidity bands only) spend their third call on `getTokenLargestAccounts`; a passed candidate reuses the holder body
     the screen retained (0 calls).
2. **Dev wallet is free.** `creator_wallet` = `coin_creator` parsed (`desk.pools.parse_pool`) from the pool account the screen retained
   (`accounts_mint_pool`), so the mint's signatures are never paged. The system address means `CREATOR_UNKNOWN`. Calls: (1) `getTokenAccountsByOwner(dev,
   mint)` -> `dev_holding_pct` (skipped when the dev is unknown); (2) `getSignaturesForAddress(POOL, 1000)` -> `graduation_block_time` = the block time of the
   pool's OLDEST signature (accepted only when the history is complete AND the oldest signature is the candidate's graduation slot), `tx_count_first_10m`
   (successful pool transactions within 600 s of it, the pool-creation transaction itself excluded) and `seconds_graduation_to_screen` (screen time = receive
   time + the screen's age, minus the BLOCK time: tested with a 30 s receive-vs-block gap). 1000+ signatures -> `HISTORY_TRUNCATED`, never paged.
3. **Quantile ties.** `quantile_groups` moves a cut that falls inside a run of equal values to the end of the run (fewer buckets may result); a 300-case
   property test shows no value is ever in two buckets and nothing is lost.
4. **Report.** `report.features_report` / `summary['features']` / an HTML section "features vs outcome": rows, entered, closed-entered, the most common missing
   `field:reason`, and per numeric feature the quantile table (n, win rate, mean pnl, `INSUFFICIENT` flags). It reads the observation `meta` (the row payload is
   stored in `meta` as well as canonically in `raw`): the existing "report never selects observation blobs" test still holds.
5. **Runner hook.** Delimited `# --- L12 hook ---` blocks only, additive: attributes, `_l12_after` (called after the L07R hook in `_isolated`, reads what became
   of the candidate from the store: a BUY fill of THIS candidate, else its last `entry` decision, else the screen reasons, else `ABORTED_BY_ERROR`), the screened
   state set after the screen decision, a health key and the recorder's daemon thread joined with a bound. No `sys.exc_info()` and no restructuring of
   `_handle_candidate` (the old `_after_screen` split is gone). A candidate that will be retried writes no row; a failed screen writes none.
6. **Production config.** `lean.json` key `features` (default null = off; `{enabled, enrich, queue_size}`, strict), validated by `load_config`, built by
   `build_runner` on `providers.low(...)`; `lean.example.json` ships it disabled.

`LowPriorityBucket` is deleted; every call goes through the shared low lane. `LANE_SHED` ends the enrichment (nothing was sent) and the rest of the fields get
that reason; `stats.shed` counts it. The row also has `screen_at` and `collected_at` (the dev/holder figures are as of a few seconds after the decision; L19 must
use `screen_at`).

## Tests / evidence
`tests/lean/test_features.py` (60 units, fixtures built from the fake world's real PumpSwap/mint layouts), `tests/lean/test_e2e_features.py` (12 end-to-end: real
runner/screen/strategy/paper/store/providers; only HTTP faked; 12 launches incl. hazards, soft rejects, a truncated pool, an unknown creator, a Helius outage and a
Jupiter outage that force retries; asserts one row per screened candidate, the real values, the call budget, the low-lane counters, a lane shed for the whole
run (not one request sent, trading unchanged), and that the trading result is IDENTICAL with the feature switched off).
```
python -m unittest discover -s tests/lean -t .   (ONE process, rc=0, on top of integration/r1 + L07R)   -> Ran 433 tests OK
```
Fail-first: the new tests on the old L12 `features.py` (same base) -> `FAILED (failures=5, errors=48)` of 71 (`/tmp/l12f/red.txt`).
Mutations (single replacement, features + e2e + report tests): 27 mutants, 27 killed (`/tmp/l12f/mutate.py`). Four survived the first set and got tests: another
candidate's fill counted as an entry, failed screens getting a row, a stale screen reused by the next candidate (needs the hook to consume it once), and a
retried candidate recorded twice (the `quote_retry` launch).

## Limitations / for the coordinator
- `dev_holding_pct` is the balance of the pool's `coin_creator` wallet only (tokens in another wallet of the same person are invisible); `coin_creator` is the
  PumpSwap pool's field, I did not verify it against live data.
- `graduation_block_time` needs a complete pool history (< 1000 signatures at collection time); for a busy pool it is missing with `HISTORY_TRUNCATED`.
- A soft reject needs 3 calls but the low lane's burst is `rate * 0.20` (2 on Helius): the third call is `LANE_SHED` unless time passes between candidates;
  production calls take time, the fake world needs `lanes.low` >= 0.3 or time between candidates (the e2e uses 0.3 and advances the clock).
- Not run against live services; the request/response shapes follow the public JSON-RPC and the repo's fixtures.
- Outcome table: only ENTERED and closed candidates have an outcome here (the not-entered ones get theirs from the L07R paths in L19).
